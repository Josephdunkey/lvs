# 25: 进度条 ETA 在「多数分镜已缓存」时过于乐观

**What to build:** 让 `lvs/progress.py` 的 ETA 在有大量缓存命中（瞬时跳过）时仍给出可信估计。

**Status:** done

**现象**：`lvs assets` 重跑时，前 N 个分镜命中磁盘产物**瞬时跳过**（不进模型），
`elapsed/done` 的**累计平均**被这些 ~0 耗时项拉低，于是 ETA 报出「20/654 ETA 23:07」
这类**过于乐观**的数字（真实量级数小时）。

**影响面**：仅出现在「**小前缀已缓存 + 大尾巴是新工作**」的场景（典型：上一次跑到很早就被打断）。
**新任务首跑**（无缓存）以及**几乎跑完的续跑**（绝大多数是缓存）都基本准确，故不紧急。

- [x] ETA 改用**近期速率**（最近 K 个「实际有耗时」的项，K≈15）而非全程累计平均
- [x] 覆盖用例：前缀 18 个瞬时跳过 + 后续 500 个各 30s → ETA 在约 15 项内收敛到「剩余×30s」量级
- [x] 保持现有 13 条 `tests/test_progress.py` 不回归（TTY / 非 TTY / 收尾 / `fmt_eta`）

---

## Comments

**来源**：30 分钟长视频压测（`long30`）现场发现。voice 阶段（无跳过）ETA 准确到分钟；
assets 阶段（前缀命中缓存）ETA 乐观约 20 倍。**刻意暂不改**：属打磨项而非缺陷，
且会动到正在跑的压测所依赖的代码路径。

## 落地（2026-09-27）

`lvs/progress.py`：新增 `ETA_WINDOW = 15` 与 `Progress.eta_seconds()` —— 用 `deque(maxlen=15)`
记最近几项各自的耗时，取平均 × 剩余。`set()` 一次跳多项（`finish()` / `set(x)`）时
**不计样本**，只把计时基准前移（否则跳变的耗时会污染窗口）。

真机形状验证（18 个瞬时 + 每个 20s 的生图，118 镜）：

```
第  1 张生图后: 剩余  99 张, ETA 00:00  (真值 33:00)   ← 窗口还没满，还在被瞬时项拖
第  5 张生图后: 剩余  95 张, ETA 08:27  (真值 31:40)
第 10 张生图后: 剩余  90 张, ETA 18:00  (真值 30:00)
第 15 张生图后: 剩余  85 张, ETA 26:27  (真值 28:20)
第 16 张生图后: 剩余  84 张, ETA 28:00  (真值 28:00)   ← 窗口填满，收敛
```

测试 13 → 19：新增 5 项（收敛、旧算法对照、未开始为 None、做完为 None、跳变不污染）。
`lvs/progress.py` 的时钟在测试里被替换成可控桩，所以"收敛"是可断言的。
