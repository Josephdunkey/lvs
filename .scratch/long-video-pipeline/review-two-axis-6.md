# 双轴审查 · 第六轮（全项目健康度）

这一轮换了**范围**（不再看单个 diff，而是整个项目）和**问法**（"项目现在怎么样了"）。
两轴各起独立 sub-agent，主代理逐条回原文件复核 —— 其中一条**跑了代码**才判定。
9 条里 **5 条成立、4 条推翻**。

## 一句话结论

**结构是健康的，记录是漂的。** 代码这边：D2「GUI 是薄壳」站得住，ffmpeg 调用只有一处，
素材分支判定只有一处，"哪几支"的规则也不再有第二份。五轮 review 反复出现的那类缺陷
（状态记账撒谎、产物不校验、静默降级、一个概念两套判据）现在都有专门的模块与测试兜住。
真正的问题集中在**文档与跟踪器落后于代码**，外加一处**回退逻辑被自己加的校验掐住**的真缺陷。

**R1 值得单独说**：票 38 加 D23 产物校验（R5）是为了挡住坏产物，结果它自己把 R4 的回退
路径掐死了 —— **两个各自正确的修复，合起来错**。现场证据：把 `cardhtml.render` 换成
"写一堆垃圾字节然后返回路径"，修复前报 `lvs.cardhtml.CardError: 卡片产物无法解码`，
修复后正常回退 Pillow、产出可解码的 1920×1080。

这正是"改完要端到端验一遍"的用处：单测里两条路径各自都过，
只有把"截图成功但产物是垃圾"这个**交叉**情况喂进去才暴露。

## 推翻的（4 条，附证据）

- **"`_wrap` 的空格断行条件是反的"** → **错**。没靠读代码下结论，直接跑了它：

  ```
  'Alpha beta gamma delta'  max_w=420 → ["Alpha beta", "gamma delta"]             空格断，对
  'averyveryverylongordindeed yes'     → ["averyveryverylongor", "dindeed yes"]  超长词才切，对
  '中文没有空格所以逐字断行才对'        → 逐字断，对
  ```
  那个 12 是"这个词是不是长到放不下"的代理判据，意图是对的 —— 读起来像 bug
  是因为没人写注释。补了注释 + 三条测试钉住，免得下次有人"修"它。

  `Workspace.try_load_shots`；真正剩下的只有 `run.py` 一处内联（已改）。写入侧确实重复（R2）。

- **"review-gui 的两个修复从未进跟踪器 —— 唯一的静默丢失"** → **错**。票 37 第 32、34 行
  逐条记着（草稿任务不进列表 / 子进程块缓冲），连测试数 318 → 337 都写了。

- **"`gui/app.py` 可能已不是薄壳"** → 不成立。只经 `registry.start` 起子进程，

## 项目健康度快照

```
代码     lvs/ 约 9000 行（最大 gui/app.py 789、shots.py 735）
测试     25 个文件约 4700 行，440 项通过
票据     42 张：38 done / 2 ready-for-agent（25、26）/ 1 ready-for-human（32）/ 1 本轮
审查     6 轮双轴，每轮成立项都有对应票据（33/38/39/41/42）
git      全项目未提交（一次都没有）
```

**最弱的结构点**：`lvs/shots.py` 把断句、beat 归位、LLM 提示词、来源策略落成、校验、
CLI 报告揉在一个模块里；纯文本逻辑与 `Workspace`/`Config`/LLM 焊在一起，**没法脱离整套栈单测**。
最有价值的改法是把纯逻辑拆成一个不碰 IO/LLM 的核心。这是大重构，本轮没做 ——
`karpathy` 的"外科手术式改动"在这里意味着**不做**，风险与本轮收益不成比例。

**第二弱**：`mark_stage` 要求调用方自己传 `status`。六轮 review 里**三次**缺陷都是
"某个阶段忘了传 / 传错 status"（票 33.1 的 build；票 26 的 assets/voice 还没做）。
让它从 `failures`/`placeholders` 自己推断，比指望每个新阶段都记得更可靠。

**测试健康**：12 处 `skipUnless` 全挂在"渲染器/浏览器在不在"上，本机全为真、没有静默跳过。
真空缺三处（按价值排序）：`shots.run_command` 的胶水层（force × 人工编辑 × 来源策略
三者交互）没有端到端测试；`studio` 的重做范围收窄只有片段覆盖；`_wrap` 原先无测试（本轮补上）。

**死代码**：`lvs/ffmpeg.py` 的 `has_ffprobe`/`has_audio`/`has_video`/`video_size` 与
`gui/store.read_parse` —— 各只有定义、全仓库无调用（逐条 grep 证实）。属既有代码，
按"不擅自删与本任务无关的死代码"的规矩先留着（已列进票 42 的待办）。

## 教训

这一轮最值钱的一条：**报告里那些"最严重发现"，有相当比例是读代码读出来的错觉**。
`_wrap` 那条如果直接改，会把一个正确实现改成错的 —— 而且没有测试会告诉你。
所以"回原文件复核"必须包含"**能跑就跑**"：只读不跑，就只是换一个人猜。
