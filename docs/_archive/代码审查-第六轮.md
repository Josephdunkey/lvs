## 一、审上一轮自己的改动 —— 抓到 3 处

### ★ 1.1 `qc` 漏接契约校验（上一轮说"下游都要验"，漏了一个）

第五轮新增了 `handoff` 契约，接了 `assets` / `tts` / `build` 三个下游。
但**还漏了 `qc`** —— 而 `qc` 恰恰是决定 **G3 门禁放不放行**的那个：
它按 `status`/`asset_path` 过滤分镜巡检，`id` 缺失会变成 0、重复 `id` 会让逐镜对位错乱，
**错的数据会被它判成"巡检通过"**，然后放行到配音。

修法之外更重要的是**判据**：加了一条架构级测试
`test_every_shots_consumer_validates_the_contract` ——
凡是**调用** `load_shots(` 的文件，必须同时出现 `handoff.check_shots_or_message`；
确属容错读的进 `_SHOTS_READ_EXEMPT` **白名单并写理由**。

> 为什么用架构级判据而不是逐个补用例：**"漏一个下游"这件事逐个测是测不出来的** ——
> 上一轮就是这么漏的。判据要按"形状"写，不能按"已想到的那几个"写。

（第一版判据没排除**定义行**，当场把 `workspace.py` 报了出来 —— 它是读取语义的 owner。已收紧为 `(?<!def )\bload_shots\(`。）

### ★ 1.2 我加的两个 GUI 错误类不受统一基类约束

扩展扫描范围到 `gui/` 后立刻暴露：`GuiError` 与 `ConfigIOError` 都不继承 `LvsError`。
已接入（分别归 `EXIT_USAGE`），并保留多重继承（`RuntimeError` / `ValueError`）不破坏既有 `except`。

### ★ 1.3 `--re-approve` 是文档里的一个**不存在的开关**

`../出图流程-v2-编排方案.md` 用陈述句写着"审批签名不可被幂等覆盖 —— 需要显式 `--re-approve`"。
核实结果：这不是 bug —— 实际行为是 `--extract` **不碰** `state` / `approved_at`（保留审批），
重新批准用 `--approve` 即可。属**方案文档的措辞**（把设计意图写成了现状），非代码缺陷。
同类还有 `--apply` / 温控参数，都明确写在"待实现清单"里，属于计划。

## 二、审框架整体 —— 抓到 3 处（含一个 P0）

### ★★ 2.1 【P0】异常 → 退出码：`errors.exit_code_for()` 与 `describe()` 是**死代码**

`cli.main()` 里**没有任何 `try/except`**。实测：

```
$ lvs cast --task t   # 定妆库 JSON 损坏
!! 未捕获异常冒泡出来: lvs.cast.CastError      ← 用户看到的是一段 Python 堆栈
   而 CastError.exit_code = 2                  ← 本该是 2，实际变成 Python 默认的 1
```

后果有两层：
1. **提示不像人话**：本该打"定妆库损坏，无法解析：<路径>"，实际打的是 traceback。
2. **脚本分不清该等还是该报警**：`StyleError`(2) 与 `BlockedError`(3) 都塌成 1。

这**正是本项目最典型的坑型**：`errors.py` 里把 `exit_code_for()` / `describe()` 写得清清楚楚，
**却从没被生产代码调用过**（上一轮修的是 `EXIT_FAILED` 从不被 `assets`/`tts` 返回 —— 同一个形状）。

修法：`main()` 变薄壳，`_main()` 干活；`main` 统一兜底三类（`LvsError` → 自带语义、
未知异常 → 1、`KeyboardInterrupt` → 1），并把 `describe()` 接上；要看堆栈设 `LVS_DEBUG=1`。

### ★★ 2.2 【P0 同源】`run_stage` 不捕获阶段异常 → `--keep-going` 对异常无效

`run_stage` 直接 `impl(...)`，异常一路冒泡。而 `run.py` 的 `--keep-going` 判的是**返回码** ——
**异常让它根本看不到失败**，于是"某阶段抛异常"就等于"整条崩"，
`--keep-going` 的语义（失败也往下走）成了一句空话。

修法：在 `run_stage` 里把 `LvsError` / 未知异常转成返回码（用 `exit_code_for` 保持语义一致），
**但放行 `KeyboardInterrupt`** —— 捕获它会让 Ctrl-C 显示成"某阶段失败返回 1"，用户以为程序卡住。

### ★ 2.3 `gui/store.py` 藏着**第 7 份**阶段顺序副本，而且架构测试**根本扫不到它**

上一轮把 `board.py` 的第 6 份修掉了，但 `_modules()` 写的是 `LVSDIR.glob("*.py")` ——
**不含子目录**，所以整个 `gui/` 一直是架构约束的盲区。

修法两条：
1. `gui/store.py` 的 `STAGES` / `STAGE_LABELS` 改读 `lvs.stage`；
2. `_modules()` 换成 `rglob("*.py")`（含 `gui/`），并把模块名推导从 `lvs.<stem>` 改成
   按相对路径推（子目录下 `f"lvs.{path.stem}"` 会变成不存在的 `lvs.app` —— 判据自己会炸）。

> 「约束只覆盖它碰巧扫到的文件」= **约束本身是假的**。这一条把盲区关上了。

### ★ 2.4 `gate.run_command` 把 `GateBlocked`(3) 错归为 2

```python
except (GateError, GateBlocked) as exc:
    return 2        # ← GateError 是 2，但 GateBlocked 的语义是 3（等人决定，不是错误）
```

改成 `return exc.exit_code` —— 与 `errors.py` 反复强调的"2 与 3 必须分开"一致。
（同一个文件里 `require()` 也是"定义了没人调用的公开 API"；`run.py` 用的是更强的 `_gate_hold`，
所以保留它但让语义正确。）

## 三、补了两个能力（都是"有真实痛点、而且不改会一直吃亏"）

### 3.1 `lvs clean` —— `.work/` 已 **923 MB** 且没有任何清理出口

实测本仓库 `.work` 有 4 个任务目录、921 MB（一个集子 603 个文件）。

**这是删除功能，所以按"宁可多问一句"设计：**
1. **默认只报告**（列出会删什么、多大、多少文件），**一个字节都不动**
2. `--yes` 才真删
3. 三种模式 `--task` / `--keep N` / `--all` **互斥**，同时给多个直接报错 ——
   猜"哪个优先"的代价是删错东西
4. **路径穿越防护**：任务名必须单段且字符受限，删除前 `_assert_inside()` 再验一次解析后路径
   （`--task ../../evil` 一律拒绝）
5. **绝不碰素材库**（`[paths].lib`）—— 那里是原始资料，删了重跑不出来

### 3.2 manifest **schema 版本号**（上一轮 P1 遗留）

原先 manifest 没有 `version`。改结构时只能靠"字段不存在就兜默认"来兼容 ——
这在**字段语义变了**（而非新增）时会静默出错：老数据被按新含义解读，不报错、只是判错。

现在：`MANIFEST_VERSION = 2`（v1 = 无字段的原始格式）；老清单按 1 读、**行为不变**；
读到**高于**本代码已知的版本 → 明确提示但不崩（静默继续比报错更危险）。

## 五、本轮最值得记住的三条

1. **审自己的改动要"换一套判据"**。上一轮我用"逐个下游补用例"验证契约校验 ——
   于是漏了 `qc`。这一轮改用**架构级判据**（凡 `load_shots(` 就必须有契约校验），
   立刻把它抓了出来，而且以后再漏也拦得住。
2. **"定义了却从不接线"是这项目最大的坑型**，且**连续两轮都在同一形状上出新洞**：
   上一轮 `EXIT_FAILED` 从不被返回，这一轮 `exit_code_for` / `describe` 从不被调用。
   → 值得写一条**通用判据**：公开的、给"上层决策"用的函数，要么有调用点，要么在测试里。
3. **判据自己也会说谎**。`_modules()` 报平安，是因为它**没扫 `gui/`**；
   第一版契约判据报 `workspace.py`，是因为它**没区分定义与调用**。
   → 每当一条判据说"全绿"，先问一句：**它的扫描范围覆盖到了吗？**
