## 2. 🔴 严重

### S01 🔴 设置页点「保存」→ 真实 API key 被掩码覆盖（不可逆）

**文件**：`lvs/gui/configio.py:149`（后端吐出掩码）· `lvs/gui/templates/settings.html:78-80`（掩码进 `value`）· 同文件 `:93-94`（非空即提交）

**问题链**（三段都在动，少一段都不成立，所以我三段都验了）：

```
① 后端  configio.read_editable():149
   "value": mask(value) if field.secret else value        →  {"value": "sk-2…2556"}

② 前端  settings.html:78-80
   <input type="password" value="${esc(f.value)}">        →  输入框里躺着 "sk-2…2556"

③ 前端  settings.html:93-94   saveConfig()
   } else if (el.type === 'password') {
     if (el.value) changes[key] = el.value;               →  "sk-2…2556" 非空 → 提交！
```

注释里写的"**密钥留空 = 不改**"是对的，但**输入框从来不是空的** —— 它被后端回显的掩码填满了。

**实测复现**（`_probe_sec3.py` P1，真 `configio` + 真 `config.toml` 的临时副本）：

```
GET /api/config 返回给浏览器的值 = 'sk-2…2556'
apply(掩码) 前: ['openai_api_key = "sk-203a…2556"   # ← 拆镜阶段必填：...']
apply(掩码) 后: ['openai_api_key = "sk-2…2556"   # ← 拆镜阶段必填：...']
>>> 🔴 真实密钥已被掩码覆盖（不可逆损坏）
```

`GET /api/config` 的真实 HTTP 响应（真 Flask test client）也确认了掩码确实从网络出去了：

```json
"app.openai_api_key": {"kind":"str","label":"LLM Key（拆镜必填）","secret":true,"value":"sk-2…2556"}
```

**风险说明**：

- **触发概率极高**：用户去设置页改 `library.dirs` 或 `library.min_score`（这是设置页最常用的两个字段），顺手点「保存」→ key 静默毁掉。
- **不可逆**：原值不在任何地方留有副本（`config.toml.bak-p2` 是 10-01 的，之后若换过 key 就真丢了）。
- **症状极具误导性**：下次 `lvs shots` 报 `LLM 返回 HTTP 401`。用户会怀疑 key 过期 / 余额 / 网络，**几乎不可能想到是自己三天前点了下保存**。排查成本以小时计。
- **不是"权限"问题**：任何能用浏览器打开这个页面的人（含被 S03 打进来的恶意网页）都能触发。

**修法（三层，第 1 层必须做，第 2 层强烈建议）**

**层 1 —— 后端拒收掩码值**（唯一不依赖前端正确性的那道闸）：

```python
# lvs/gui/configio.py —— 在 is_secret_key() 下面加
_MASK_CHAR = "…"          # 与 mask() 用的那个字符保持一致
_SET_SENTINEL = "已设置"   # mask() 对短值的产物


def looks_masked(value: Any) -> bool:
    """这个值是不是 read_editable() 自己吐出去的掩码？

    ★ 为什么必须在**后端**挡：前端只要哪天忘了判空（或者浏览器自动填充、
      或者有人直接 curl 打 /api/config），掩码就会被当成"用户填的新密钥"
      写进 config.toml —— 而它是一串**永远不可能通过校验**的字符串，
      等于把真 key 静默删掉。后端是最后一道，也是唯一不依赖前端正确性的那道。
    """
    text = str(value or "")
    return _MASK_CHAR in text or text == _SET_SENTINEL
```

```python
# lvs/gui/configio.py —— apply()，紧跟在 bad 校验之后
    bad = sorted(set(changes) - set(_BY_KEY))
    if bad:
        raise ConfigIOError(f"这些键不允许在界面里改：{bad}")

    # 掩码不是密钥。有人（前端 bug / curl / 脚本）把回显值当新值提交时，
    # 宁可报错让他重填，也绝不能让真实密钥被一串省略号顶掉。
    masked = sorted(
        key for key, raw in changes.items()
        if _BY_KEY[key].secret and looks_masked(raw)
    )
    if masked:
        raise ConfigIOError(
            f"拒绝写回：{masked} 提交的是页面回显的**掩码**，不是真密钥。"
            "要换密钥请填完整的新值；不打算改就**别提交这个字段**（留空即可）。"
        )
```

- **不需要用户做任何"傻事"**：只要 GUI 开着，用户切到任意标签页浏览，那个页面里一段 `<form action="http://127.0.0.1:8730/api/task" method="post">` + 一段 JS 自动提交，就能：建任意任务、**覆盖已有拍摄稿**（= 毁掉几小时的拆镜成果）、把来源策略重置成 auto、停掉正在跑的 30 分钟生图 job。
- **DNS rebinding 更进一步**：`TRUSTED_HOSTS` 没配 → 恶意域名解析到 127.0.0.1 后，`Host: evil.com` 会被 Flask 照收；这时浏览器的 origin 也是 `evil.com` → 变成**同源**，连 `/api/config`（含打码 key、素材库路径）、`/api/doctor`（含本机环境细节）、`/api/task/<n>/shots`（含全部旁白与提示词）都能**读**。
- **威胁模型校准**：这不是"公网可打"，是"**本机浏览器里任何一个页面可打**"。对一个单人本机工具来说，这个概率不低（谁没边跑渲染边刷网页），后果是"算力白烧 + 成果被覆盖"，够 🔴。
- 注意 `/api/task/<name>/pick`（`multipart`）也在简单请求之列，但它需要 `request.files.get("image")` 真有文件，跨站表单拿不到用户的文件，所以危害有限（只会拿到 400）。

```python
# lvs/gui/app.py —— create_app() 里，注册路由之前插入

    # ---- 本机界面的两道门（S03）------------------------------------------
    #
    # 背景：浏览器对 multipart / urlencoded 的 POST **不发预检**（"简单请求"），
    # 所以"只绑 127.0.0.1"挡不住跨站写。实测跨站表单能建任务、能改 source_mode、
    # 能停掉正在跑的 job。这里加两道**不需要 cookie、不需要前端改动**的门。
    #
    # 没做 CSRF token 的原因：token 要在页面里种、每个 fetch 都带上，
    # 得同时改 base.html / app.js / 全部 POST 测试。下面这两道已经堵住了
    # 「浏览器跨站」这个真实入口，token 可以留到以后需要更严的隔离时再上。

    @app.before_request
    def _host_guard():
        """挡 DNS rebinding：恶意域名解析到 127.0.0.1 后，Host 头会是那个域名。

        （Flask 3.0.3 还没有 TRUSTED_HOSTS，所以自己写。升到 3.1+ 后可换成
          app.config["TRUSTED_HOSTS"] = [...]，语义一样。）
        """
        host = (request.host or "").rsplit(":", 1)[0].strip("[]").lower()
        if host not in ("127.0.0.1", "localhost", "::1"):
            return jsonify({"error": f"不受信任的 Host：{host}；本界面只服务本机"}), 421
        return None

    @app.before_request
    def _same_origin_guard():
        """挡跨站写。

        浏览器**一定**会给跨站 POST 带 Origin（同源的普通表单也可能带，
        那就等于 origin == host_url，照样放行）。没有 Origin 的 = curl /
        本机脚本 / pytest，放行 —— 它们本来就能随意读写磁盘，拦它们没意义。
        """
        if request.method in ("GET", "HEAD", "OPTIONS"):
            return None
        origin = request.headers.get("Origin")
        if origin is None:
            return None
        if origin.rstrip("/") != request.host_url.rstrip("/"):
            return jsonify({"error": "拒绝跨站写入（本机界面不接受外部 Origin）"}), 403
        return None
```

### S04 🟠 SRT 正文零转义：一句旁白能把字幕文件结构撑坏

**文件**：`lvs/tts.py:528`（`_srt_text` 不存在 —— 这就是问题）

```python
        out.append(f"{idx}\n{_fmt_ts(t0)} --> {_fmt_ts(t1)}\n{text}\n")
```

`text` 来自 `split_display_lines(narration, …)`，而 `narration` 是 `shots.json` 里的自由文本（人工可改、LLM 可产）。`split_display_lines` 逐字符扫，`\n` 只会被当成普通字符塞进 `buf`，**不做任何过滤**（已实测 `any(chr(10) in t for _,_,t in split_display_lines(...))` → `True`）。

**实测**（`_probe_sec3.py` P2，`narration = "第一行\n第二行 --> 0:00:01,000\n00:00:02,000\n\u001a\u0000 残留"`）：

```
1
00:00:00,000 --> 00:00:00,333
第一行
第二行 --> 0:

2
00:00:00,333 --> 00:00:00,643
00:01,000
00:

3
00:00:00,643 --> 00:00:01,000
00:02,000
 残留
```

一条镜的旁白变成了**三个字幕块**，正文里出现了 `00:01,000` 这种"看起来像时间轴"的行，NUL 与 `\x1a` 也原样进了文件。

**风险说明**：

- 播放器/`libass` 对"正文里像时间轴的行"处理不一致：宽松的（ffmpeg 内置）忽略，严格的（部分剪辑软件/导入工具）会解析错乱 → 字幕整段错位。这类 bug 用户看到的现象是"字幕怎么全乱了"，但根因在稿件里一个换行，**极难定位**。
- `\x1a`/NUL 会让某些工具判定文件为"二进制"直接拒收。
- 不是"注入"（这里没有解析器能执行代码），是**数据完整性**问题。但如果旁白来自 LLM，而稿件又来自不可信来源（比如把网上找的翻译稿粘进去），就等于"外部文本能改写你的字幕文件结构"。

**修法**：

```python
# lvs/tts.py —— 加在 _fmt_ts() 附近
_SRT_C0 = re.compile(r"[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]")     # 控制字符（含 SUB/ESC）
_SRT_BREAK = re.compile(r"[\r\n\u2028\u2029]+")                 # 各种换行


def _srt_text(text: str) -> str:
    """把一行旁白变成合法 SRT 正文。

    实测（2026-10-04 安全审查）：旁白里带换行会让一条字幕裂成三条块；
    正文里的 --> 会让一部分严格解析器把下一行当时间轴；SUB/NUL 直接进文件。
    旁白是"人工手改 + LLM 生成"都可能带进来的自由文本，所以**出口必须净化**，
    不能指望上游干净（split_display_lines 是按字切分的，它不管这个）。
    """
    text = _SRT_C0.sub("", str(text or ""))
    text = _SRT_BREAK.sub(" ", text)         # 换行 -> 空格：单行字幕，不裂块
    return text.replace("-->", "→").strip()  # 别让正文长得像时间轴
```

### S07 🟠 密钥只能"写进文件"，没有环境变量 / `.env` 覆盖通道

**文件**：`lvs/config.py`（无覆盖层）· `lvs/llm.py:64`（`api_key=str(config.get("app.openai_api_key"))`）· `lvs/assets.py:1147`（`config.get("pexels.api_key")`）

**实测**：`grep -rn "os.environ" lvs/` 只命中 3 处，**没有一处**是"从环境读密钥"：

```
LVS_CONFIG     —— 指定 config 路径
LVS_BROWSER    —— 指定无头浏览器（cardhtml.py）
LVS_DEBUG      —— 调试开关
```

**风险说明**：

- 十二要素应用的标准做法是"配置走环境，密钥不进文件"。这里反过来：**要跑拆镜就必须把 key 落到磁盘**。
- 后果是 S01/S02/S06 的暴露面被**结构性放大**：不是"某段代码写漏了转义"，而是"设计上只有一条把密钥写进文件的路"。CI/容器/多机器场景下尤其难受（要么 commit 配置，要么每台机器手动填）。
- `.demo/*.toml` 之所以会带真钥，根因也在这：**没有别的办法**让一份可用的演示配置跑起来。

**修法**（`config.py` 加一层覆盖，动 1 个文件；优先级：环境 > 文件，与主流工具一致）：

```python
# lvs/config.py —— Config 构造完之后，用环境变量覆盖那几个敏感键
#
# 约定：`LVS__<SECTION>__<KEY>`（双下划线分层，避免和 TOML 的点号键盘冲突）
#   LVS__APP__OPENAI_API_KEY=sk-xxx
#   LVS__PEXELS__API_KEY=xxx
# 只认**已经存在于配置模式里**的键，不做"任意键注入"——
# 否则一个环境变量就能往配置里塞任意路径（那比硬编码 key 更危险）。
_ENV_OVERRIDE_PREFIX = "LVS__"
_ENV_OVERRIDE_KEYS = {
    "APP__OPENAI_API_KEY": "app.openai_api_key",
    "APP__OPENAI_BASE_URL": "app.openai_base_url",
    "APP__OPENAI_MODEL_NAME": "app.openai_model_name",
    "PEXELS__API_KEY": "pexels.api_key",
}


def _apply_env_overrides(data: dict[str, Any]) -> dict[str, Any]:
    """环境变量 > 配置文件。白名单制：只有上面那几个键能被覆盖。"""
    for env_name, dotted in _ENV_OVERRIDE_KEYS.items():
        raw = os.environ.get(_ENV_OVERRIDE_PREFIX + env_name)
        if raw is None or raw == "":
            continue
        *sections, leaf = dotted.split(".")
        node = data
        for section in sections:
            node = node.setdefault(section, {})
        node[leaf] = raw
    return data
```

然后在 `load()` / `Config.from_file()` 的出口调用一次 `_apply_env_overrides(data)`。配套给 `doctor.py` 的输出加一行来源标注（**不回显值**）：

```python
# lvs/doctor.py —— check_llm() 里，让用户知道"这个 key 是从哪来的"
# 现在只打 "已配置（provider/model/base）"，加一个来源提示：
#   "已配置（来源：环境变量 LVS__APP__OPENAI_API_KEY）"
# 或 "已配置（来源：config.toml）"
```

> 这条不是"修复漏洞"，是"**把 S01/S02/S06 的根因拆掉**"。优先级可以排在 S01/S02 之后，但别漏 —— 它是唯一能让"密钥不落盘"成为可能的改动。`.env` 支持（`python-dotenv`）建议**不做**：又多一个会被误 commit 的文件（`.env` 必须在 `.gitignore` 里，而"记得加"这件事本身就会失败）。

### S09 🟡 `Workspace.dir` 不校验 `task`（当前不可达，但该有断言）

**文件**：`lvs/workspace.py:107-109`

```python
    @property
    def dir(self) -> Path:
        return self.root / WORK_DIRNAME / self.task        # ← task 未校验
```

对比 `lvs/gui/store.py:90-102` 的 `task_dir()`：那里做得很对（拒 `/`、拒 `\`、`resolve()` + `parents` 双重判定）。

**实测为什么现在不可达**：

```
slugify('../../evil')  = 'evil'          ← 斜杠被吃掉了
slugify("a'b")         = 'a-b'           ← 单引号被吃掉（这也是 concat.txt 安全的根因）
slugify('a\nb')        = 'a-b'           ← 换行被吃掉
slugify('a"; rm -rf')  = 'a-rm-rf'
```

CLI 唯一入口 `cli._resolve_task()` 对 `--task` 和 `--manuscript` 都过 `slugify()`。GUI 走 `store.task_dir()`。所以两条路都够不着未净化的 `task`。

**但它仍然是"防御深度"缺口**：`Workspace(task=...)` 是个 public dataclass，任何新代码（或测试、或以后加的插件）都可以直接构造。一旦构造出 `Workspace(task="../../..")`，`ws.path("logs")`、`ws.dir` 就全在仓库外了 —— 而且**没有任何一处会报错**。

**修法**：

```python
# lvs/workspace.py —— Workspace.dir
    @property
    def dir(self) -> Path:
        """`<root>/.work/<task>`。

        ★ 这里加断言，不是为了"现在"——slugify() 已经把危险字符吃掉了，
          CLI 与 GUI 两条路都够不着未净化的 task。是为了"以后"：这个类是
          public 的，谁都能 Workspace(task=...)；而一旦 task 里带 `..`，
          ws.path("logs") 会静默写到仓库外，**没有任何一处会报错**。
          防御深度比"相信我现在的调用方都对"更便宜。
        """
        name = str(self.task or "")
        if not name or "/" in name or "\\" in name or ".." in name:
            raise ValueError(
                f"任务名非法（不许含路径分隔符或 `..`）：{self.task!r}；"
                "构建任务名请用 `lvs.workspace.slugify()`"
            )
        return self.root / WORK_DIRNAME / name
```

### S10 🟡 关键变更没有审计痕迹（谁在什么时候改了 config / shots）

**现状**（实测 grep）：`lvs/gui/app.py` 写 `config.toml`（`:217`）和 `shots.json`（`:282` / `:478`）三条路径，**一条日志都不打**；全包也没有任何 `logging` 模块的使用（`grep -rn "import logging" lvs/` 为空）。

**风险说明**：

- 安全事件里最贵的东西是"**能不能复盘**"。S01（key 被写成掩码）如果发生在昨天，用户今天唯一能看到的痕迹是 `config.toml` 里那串省略号 —— 不知道是谁、什么时候、通过哪个入口写的。
- 对单人本机工具，"审计日志"不需要很重：**写操作落一行 JSONL** 就够了。

**修法**（在已有的写操作旁边加一行，不引入新依赖）：

```python
# lvs/config.py 或新建 lvs/audit.py —— 极简审计日志
def audit(event: str, **fields: Any) -> None:
    """把一次**会改变磁盘状态**的写操作记一行 JSONL。

    只记"谁改了什么"，**永不记值**（密钥/旁白都在此列）——
    否则审计日志自己就成了新的泄露面（这是最常见的二次翻车）。
    位置：`<root>/.work/_audit.jsonl`；.work/ 已经在 .gitignore 里，不进 git。
    """
    import json, os, time
    rec = {"ts": time.strftime("%Y-%m-%dT%H:%M:%S"), "event": event, "pid": os.getpid(), **fields}
    try:
        path = _audit_path()
        path.parent.mkdir(parents=True, exist_ok=True)
        with path.open("a", encoding="utf-8") as fh:
            fh.write(json.dumps(rec, ensure_ascii=False) + "\n")
    except OSError:
        pass          # 审计失败绝不能影响主流程
```

### S11 🟡 `_escape_style` —— 已核实**打不穿** ffmpeg，但写错会**静默**退化

**文件**：`lvs/build.py:477-478` 与 `:557` / `:579`

```python
def _escape_style(style: str) -> str:
    return style.replace("'", "")

...
    style = _escape_style(str(config.get("build.subtitle_style", DEFAULT_SUBTITLE_STYLE)))
    ...
    video_part = f"[0:v]subtitles={rel_srt}:force_style='{style}'[v]"
```

**这一条要先给结论**：**不是注入漏洞**。我用真 ffmpeg（imageio-ffmpeg 7.1）跑了三种注入，全部被 ffmpeg 在参数解析阶段拒掉：

```
[正常]          style=Fontname=Arial,Fontsize=20                     rc=0     ✅
[注入-引号闭合]  style=Fontsize=20'[0:v]drawtext=text=pwned;...        rc≠0
                → Failed to set value '...[0:v]subtitles=in.srt:force_style='Fontsize=20[0:v]drawtext=...'
                  for option 'filter_complex': Invalid argument
[注入-换行]      style=Fontsize=20 + 换行 + [0:v]drawtext=...            rc≠0   同上
[注入-反斜杠]    style=Fontsize=20\'[0:v]null                           rc≠0   同上
```

原因（值得记下来，免得以后有人"优化"掉这行）：`force_style='...'` 里那对单引号在 **filtergraph 第一层**把 `:` `,` `;` `[` `]` 全部变成字面量，而剥掉单引号之后**再也闭合不了**那个引用 → 整串被当成一个畸形参数。**单引号剥离在这里就是完备的转义**。

**剩下的真问题是"静默降级"**（这条归入本维度是因为它由"配置注入尝试"暴露出来）：

```python
# lvs/build.py:596-598

            print("⚠️ 烧字幕失败（可能是 ffmpeg 缺 libass，或字体缺失），先输出无字幕版：")
            print("   " + str(exc).splitlines()[0])
```

用户在 `config.toml` 里把 `build.subtitle_style` 写坏了（多了个引号、带了个换行），`lvs build` **不会失败**，会安静地产出一个**没有字幕的成片**并打印一行警告（那行警告在几百行日志里很容易滑过去）。用户半小时后看着成片纳闷"字幕呢"。

**修法（在失败回退前，把"配置里的值"和"环境缺东西"分开）**：

```python
# lvs/build.py —— _finalize() 的烧字幕失败分支
        except FFmpegError as exc:
            first = str(exc).splitlines()[0]
            # ★ `build.subtitle_style` 是**用户能写坏的东西**，不该和
            #   "这台机器没装 libass"混在同一个警告里。实测：把 style 写错会
            #   让 ffmpeg 在参数解析阶段就拒掉整个 filter_complex，症状与
            #   "缺字体"一模一样，但解药完全不同（一个是改配置，一个是装东西）。
            if "Invalid argument" in first and "filter_complex" in str(exc):
                print("⚠️ `build.subtitle_style` 不是合法取值，ffmpeg 拒绝了整个滤镜：")
                print(f"   当前值：{style!r}")
                print("   先输出无字幕版；改对 `[build].subtitle_style` 再 `lvs build --force`。")
            else:
                print("⚠️ 烧字幕失败（可能是 ffmpeg 缺 libass，或字体缺失），先输出无字幕版：")
            print("   " + first)
```

> **别做**：不要为了"更安全"去写一套 `_escape_style` 的强化版（把 `,` `:` 也剥掉）。那会误伤合法取值（`Fontname=Arial,Fontsize=20` 里的逗号是**必须的**），把一个已经正确的转义改成错的。

### S12 🟡 `jobs.py:337` 把完整 argv 落盘并 SSE 广播（当前无密钥项，属未来风险）

**文件**：`lvs/gui/jobs.py:337`

```python
        job.emit(f"[gui] $ {' '.join(job.argv)}")
```

`emit()` 的内容会同时进**环形缓冲（SSE 推给浏览器）**和 **`.work/<task>/logs/*.log`（落盘）**。

**实测：现在安全**。我逐个过了一遍 `STAGE_SPEC`（`lvs/stage.py` 的 `Option` 定义）：`force / source / visual / style / style_file / no_llm / no_library / only / no_cast_gate / skip_gates / keep_going / demo / redo / action / prompt / seed / redo_shots / stop / yes / out / base / lines / llm` —— **没有一个是密钥类**。而且 `build_argv` 有 `_UNSAFE_TEXT`（控制字符）+ `MAX_TEXT=4000` 两道校验。

**风险说明**：这是**前瞻性**的。哪天有人加一个 `--api-key` 之类的开关（很自然会想做：`lvs publish --llm` 已经有 `--llm` 了，下一步可能就想加 `--llm-key`），这一行会**当天把密钥写进日志文件并推给浏览器**，而且日志还会被 `lvs board` / GUI 回看功能展示出来。这类事故的特点是"加开关的人根本不会想到要去改 jobs.py"。

**修法（在日志唯一出口处做，而不是在调用方做）**：

```python
# lvs/gui/jobs.py —— 加在 _run() 之上
_SECRET_ARG = re.compile(
    r"(?i)^(--?(?:api[_-]?key|key|token|secret|password|passwd|auth))$"
)


def _redact_argv(argv: list[str]) -> list[str]:
    """把命令行里的密钥类参数打码后才进日志。

    ★ 为什么要在**这里**做：argv 会同时进 SSE（推浏览器）与 .work/.../logs/*.log
      （落盘 + 被 board / GUI 回看），是日志的唯一出口。放在这里，
      以后谁加了 --api-key 都不会踩坑（放在调用方，加开关的人看不见这条规则）。
      当前 STAGE_SPEC 里没有任何密钥项 —— 这是给未来上的保险，不是补锅。
    """
    out: list[str] = []
    hide_next = False
    for token in argv:
        if hide_next:
            out.append("***")
            hide_next = False
        elif _SECRET_ARG.match(token):
            out.append(token)
            hide_next = True
        else:
            out.append(token)
    return out
```

## 7. 架构改进建议（安全视角，接维度 1 的 A1–A6、维度 2 的 A7–A9）

### S-A1 ★ 「密钥」必须只有一个出口，且出口在**最内层**

**现状**：密钥的读取散在 3 处（`llm.py:64`、`assets.py:1147`、`configio.py` 的编辑面），每一处都得自己记得"要打码/不要回显/要校验"。

**问题**：S01 就是这么来的 —— "打码"做在 `read_editable`（读侧），但"不许把掩码写回去"没人管（写侧）。**读侧打码、写侧不设防**，这是所有"掩码回写"事故的标准形状。

**建议**：在 `lvs/config.py` 里给密钥一个**类型**，而不是一个字符串：

```python
# lvs/config.py —— 让"密钥"成为一个不能被当成普通字符串用掉的类型
@dataclass(frozen=True)
class Secret:
    """一个密钥值。**repr / str 一律给掩码** —— 这样日志、异常消息、
    调试打印无意间带出它时都是安全的（默认安全，而不是"记得打码"）。

    真值只能通过 `reveal()` 拿到，`grep -rn "reveal()"` 就能审计
    "全项目有哪些地方真的需要明文"—— 预期结果应该只有 2~3 处
    （LLM HTTP 头、Pexels HTTP 头），那就是完整的密钥使用面。
    """
    _value: str

    def reveal(self) -> str:
        return self._value

    def masked(self) -> str:
        v = self._value
        return (v[:4] + "…" + v[-4:]) if len(v) > 10 else ("已设置" if v else "")

    def __str__(self) -> str:
        return self.masked()

    def __repr__(self) -> str:
        return f"Secret({self.masked()!r})"
```

配合 `looks_masked()`（S01 层 1）与"写回只接受 `Secret` 或 `None`"，S01/S06/S12 三类问题会**同时**结构性消失（不是被补丁堵住，而是构造不出来）。

### S-A2 ★ 把"出口净化"做成一条流水线规则，而不是每处各写一遍

**现状**：本维度里三个问题（S04 SRT、S05 投稿路径、S11 style）**形状完全一样**：

> 内部数据 → 交给一个**外部解析器 / 外部人看**的产物 → 中间没有任何净化

- `narration` → SRT 文件（外部解析器：播放器/剪辑软件）
- `Path` → `bilibili.md` / `meta.json`（外部读者：B 站观众）
- `build.subtitle_style` → ffmpeg filtergraph（外部解析器：ffmpeg）

**建议**：给项目立一条**明文规矩**（写进 `CONTRIBUTING` 或 `docs/`）：

> **任何"内部数据 → 外部产物"的边界，都必须在**边界处**做一次显式净化，并配一条守卫测试。**
> 净化函数命名统一为 `_for_<consumer>()`：`_srt_text()` / `_display_path()` / `_escape_style()`。
> 上游（切分、排版、拼装）**不负责**净化 —— 那是两个 owner 干一件事。

这条规矩的收益不只是这三个 bug：它让"新增一种产物/一个新外部工具"时，有一个**照抄 checklist** 的地方（正好对应维度 2 的 A9）。

### S-A3 ★ 威胁模型要写下来，否则"本机工具不做鉴权"会被反复误判

**现状**：`serve()` 的 docstring 写着"只绑 127.0.0.1 … 也不做鉴权"——**这个判断本身是错的**（S03：本机 ≠ 只有你，浏览器里任何一个页面都是潜在调用方），但它错得很合理，因为**威胁模型从来没写下来过**，每个人（含 agent）都在用直觉填。

**建议**：在 `docs/` 里加一页 `威胁模型.md`，明确四件事：

1. **谁能在本机跑代码** = 你本人 + 你放的 agent + 你开的浏览器里加载的**任意**网页 → 所以该防的是"浏览器发来的请求"，而不是"局域网"；
2. **哪些东西值得保护**：API key（钱）、`.work/` 里几十分钟的算力产物（时间）、素材库路径（隐私）；
3. **哪些不做**：不做多用户、不做网络加密、不做权限分级——**明确写下"不做"比默认不写更有价值**（否则下一个人会以为该做而做一半）；
4. **每条防线的失效模式**：`.gitignore` 挡不住 `git add -f`；`127.0.0.1` 挡不住浏览器跨站也挡不住 DNS rebinding；掩码挡不住 `curl`。

### S-A4 ★ 把"密钥不进仓库"变成 CI 红线，而不是靠人记

**现状**：`.gitignore` 是**唯一**的防线，而它天然有"漏一个模式就全泄"的性质（S02 就是漏了 3 个文件）。本次审查**自己**也把 key 抄进了报告（S06 #5）—— 说明"靠人记得别抄"是不可行的。

**建议**：三层，成本递增：

1. **测试层**（今天就能上，见 S06 的 `test_no_secret_leak.py`）—— 高熵串 + 真实值反查，跑在 pytest 里；
2. **提交期**（可选）：`.githooks/pre-commit` 调同一个测试（`git config core.hooksPath .githooks`）；
3. **推送期**（真有远端时）：GitHub secret scanning / gitleaks。

第 1 层是最划算的 —— 它把"自觉"换成"断言"，而**这次审查的证据表明自觉已经失败过一次**。
