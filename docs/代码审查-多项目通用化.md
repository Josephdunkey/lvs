# 代码审查 · 多项目通用化（2026-10-03 第二轮）

> 范围：把 `lvs` 从"为《挪威的森林》写的一套"改造成"服务任意书 / 任意题材的流水线"。
>
> 结论：**可以合并。** 新增/改动文件 `pyflakes` 零告警；受影响测试面全绿；
> 真实项目（`config.toml`）已切换到新机制并**验证与旧显式配置等价**。
>
> 这一轮最值钱的两条不是"加了什么功能"，而是
> **§3.1 我自己写的 30 个预设踩了项目自己的红线**（被测试抓出来），
> 与 **§3.2 我自己引入的 `_cast` / `cast` 不一致**（靠"两端同名"的测试守住）。

## 一、需求与判据

用户的要求是：**"不止用于挪威的森林这一个项目，以后也会用于各种项目"**。

把这句话翻译成可验证的判据，才有意义：

| 判据 | 怎么验证 |
|---|---|
| 换一本书**不需要改代码** | 风格可外部声明；`lvs styles` 能列出 |
| 换一个题材**不需要改代码** | 30 个内置预设覆盖六大类；不够时写项目风格文件 |
| 接一本新书**不需要猜路径** | `lvs init` 建骨架 + 生成项目 config + 体检待办 |
| 手填的路径越少越好 | `[paths].lib` 一配，定妆库 / 定妆卡 / 风格文件全部派生 |
| 换书后出错要**报错**而不是静默 | 定妆卡多份时不猜；未知风格列候选；路径不一致有测试守 |
| 流水线常数不能硬编码 | "必须纯黑白"改成**风格属性**（`monochrome`） |

## 三、发现并修掉的问题

### ★ 3.1 我自己写的 30 个预设，踩了项目自己的红线

写完 30 个预设之后，我把测试补上——**测试当场否掉了 13 个预设**：

| 问题 | 命中 | 为什么是问题 |
|---|---|---|
| 含否定词 | `pen-ink-sketch`（`no tonal wash`）、`minimal-line-art`（`no shading and no fill`）、`gongbi-color`（`no visible brush texture`）、`flat-vector-editorial`（`no gradients or outlines`）、`pixel-art-retro`（`no anti-aliasing or blur`） | cfg=1.0 模型没有负向引导，**否定句里的名词会被原样画出来**。`no shading` → 出现 shading |
| 标了单色却没有正面黑白陈述 | 7 个（`chinese-ink-wash` / `charcoal-drawing` / `pen-ink-sketch` / `linocut-graphic` / `dark-fantasy-etching` / `minimal-line-art` / `old-photo-sepia`） | 靠"不说彩色"是无效的；必须正面写 `grayscale only` |
| 没声明单幅 | `historical-documentary`（**默认预设**） | 可能出联画 / 分格 |
| 单色标记与画面不符 | `old-photo-sepia` | 棕褐是**有色度**的，标成单色会让 `lvs qc` 把正常棕调报成「彩度异常」 |

> **这一条是本轮最有价值的发现**：我一边在文档里写着"三条红线"，
> 一边自己写的内容全踩了 —— 因为**红线只写在文档里时没人会去看**。
> 现在它们变成了 `tests/test_styles.py` 里的断言，下一个加预设的人会被拦住。
>
> 而且我特意把否定式判据做得**比 `C021` 更严**：C021 的名词表只覆盖
> `people / text / face` 那一类，管不到 `shading / gradients / anti-aliasing`。

### ★ 3.2 我自己引入的 `_cast` / `cast` 不一致（自查发现）

`lvs init` 建的骨架里有 `_cast/`，而 `cast.cast_dir()` 从 `[paths].lib` 派生的是 `lib / "cast"`。

后果是**静默的**：`init` 建 `_cast`、`cast` 读 `cast` —— 定妆库会凭空多出一个空目录，
不报错、不警告，直到"为什么定妆照读不到"为止。

修法：加常量 `LIB_CAST_DIRNAME = "_cast"`，并补一个测试
`test_lib_cast_dirname_matches_scaffold` 把"两端同名"钉死。

> 这正是本轮要消灭的那类问题：**接第二本书时手填 5 个路径，填错不报错**。

### 3.3 英文代词没有单词边界 → 会把英文稿改成乱码

`_first_pronoun_outside_slot` 的边界判据是中文的（`其他 / 他们 / 自我` 的构词字符）。
对英文等于**没判**：`he` 是 `the / her / when` 的子串。

```
the man is here   →   t{X} man is here
her coat was wet  →   {X} r coat was wet
```

修法：**分语言**。ASCII 代词用 `(?<![A-Za-z])…(?![A-Za-z])` + `IGNORECASE`（`He` = `he`）；
CJK 代词继续用复合词判据。

### 3.4 lint 词表只有英文 → 中文锚定全是误报

`_FACE_WORDS` / `_PERSON_WORDS` / `_PROP_WORDS` / `_EXPRESSION_WORDS` 全是英文词。
用中文写设定的项目跑 `--lint` 会**误报 A-nosubject**（"一个女大学生"里没人称名词）。

修法：四张词表各加中文词，**并入同一个正则分组**（中文不受 ASCII lookaround 影响，
所以不需要语言检测，也不会互相干扰）。

### 3.5 默认预设没声明单幅

`historical-documentary` 是**默认**预设，却是 30 个里唯一没写
`single full-frame composition` 的 —— 而它正是"历史纪录片"这种最容易出联画的题材。

### 3.6 一个永远返回 `None` 的死函数

`styles.lib_dir_from(reg)`：想从注册表反推素材库根，写了却推不出来（信息不在注册表里）。
**留着就是给下一个人挖坑** —— 他可能真的去调它，然后拿到 None 而困惑。

修法：删掉，改成把 `lib` 当参数传进 `render_catalog()`。

### 3.7 提示词把 `--config` 的位置写错

`lvs init` 输出里写的是 `lvs --config X styles`，但 `--config` 挂在子命令上
（`lvs styles --config X`），照抄会得到
`invalid choice: 'config.demo.toml'`。

修法：改正提示文案。（顺带暴露一个小摩擦点：顶层不支持 `--config`。
这属于 UX 改进，留到下一轮 —— 见 §六.3。）

### 3.8 流程教训：**不要用脚本批量改源码**

这一轮我几次用 Python 脚本对 `cast.py` / `migrate.py` 做"批量正则改写"，
结果**改坏了 Python 结构**（多插括号、吃掉闭合括号、把 `\1` 写成控制字符 U+0001），
每次都要回头手工修。

> **教训**：源码改写要么用 Edit/Write 精确替换，要么用能保证语法正确的工具
> （如 `ast` + `unparse`、codemod）。**正则批量改源码是不可靠的** ——
> 它改完不会报错，只会让下一次导入炸掉。
>
> 内容文件（Markdown / TOML）用脚本批量改是安全的（错了只是文字不对，不会崩）。

## 六、已知遗留

1. **顶层不支持 `--config`**：目前必须写成 `lvs styles --config X`。
   `lvs --config X styles` 会报 `invalid choice`。两种写法都该支持。
2. **`lvs init` 不会替你写定妆卡与拍摄稿** —— 这是刻意的（那是创作）。
   但它会在体检里说清楚还缺什么。
3. **没有"项目列表"**：同时做多本书时，靠记住各自的 `config.<名>.toml` 文件名。
   可以加 `lvs projects` 列出仓库根下所有 `config.*.toml` 与其素材库。
4. **`[styles]` 内联写法与项目文件同名时，项目文件优先** —— 有测试钉住，
   但"想临时覆盖项目风格"时只能靠 `--style-file`（写一个临时 TOML）。
   可以加 `--style-suffix` 一次性覆盖。
5. **风格预设的 suffix 没有自动 lint**：`tests/test_styles.py` 只检查内置的；
   项目自定义的风格文件里写了否定词，目前**不会**被拦。
   应把这条 lint 接到 `lvs styles` 的输出里（像 `cast --lint` 那样）。
   → **这是下一轮最该补的一条**，因为它正是 §3.1 那类问题的通用解。
