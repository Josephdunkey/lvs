> 与主报告§8 的分工：主报告 §8 算的是**“续跑起步要读多少东西”**（一次性）；

## §0 一句话结论

**费的不是“读得多”，是“同一段历史被重发了 845 遍”。**

```
成本  ≈  模型调用次数  ×  每次调用时的上下文长度
78,111,691  =      845      ×        92,440
```

真正“新进来”的信息（工具输出）只有 **1.94 MB ≈ 60.7 万 token**，占输入总量的 **0.8%**；
其余 **99.2%** 是把已经在上下文里的东西（系统提示 + 前面所有轮次 + 所有工具输出）**逐条重新发送**。

## §2 钱花在哪：八九成字节是工具输出，但真正的新信息只占 0.8%

### 2.2 但工具输出的**真实体量**并不大

| 指标 | 数值 |

> 对比：工具输出只有 **1.94 MB**，却让 input 累计到 **78.1 M token**。
> 差距的来源就是§2.3 的重发机制。

### 2.3 重发机制（这是本报告最想讲清楚的一节）

Agent 是**无状态**调用：每一次调用，客户端都把“系统提示 + 历史全部”重新发一遍。于是：

```
第 1 次调用  → 发 2.7 万
第 2 次调用  → 发 2.7 万 + 第1次的输出
...
第 845 次调用 → 发 前 844 次的全部（在压缩后仍然有 ~9 万）
```

如果上下文不压缩，845 次调用的 input 会呈**二次方增长**（总计 ≈ N²/2）。
本会话赖 **10 次压缩**（每到 ~18 万就压）把它拉回**线性**——但代价是：每个压缩区间里，“常驻”都稳定在 **8.8–10 万**（见 §2.4）。

**96.9% 命中缓存** 说明前缀一直没变——省了钱，**但 token 计数上仍全额计入**，这就是“看着吓人”的直接原因。

## §3 为什么“这个项目”格外费：六个放大因子（全部实测）

### F1 真相源分散 → 一条消息要 46 次工具调用

| 指标 | 数值 |
|---|---|
| 本会话工具调用 | **1,056** 次 |
| 用户回合 | 23 个 |
| **平均** | **45.9 次 / 回合** |

为什么需要这么多次？因为每张“图”都只能一块一块拼：状态在 `.work/<task>/gates.json` + `manifest.json` + `shots.json`；
约定在 `MEMORY.md` + 当日日志；流程在三份手册；代码散在 48 个 `.py`。**没有一个命令能一次说完“现在在哪、下一步干吗、该改哪行”。**

### F2 同一个文件被反复重读（重读热点）

| 次数 | 目标 | 为什么重读 |
|---|---|---|
| **46** | `Select-String lvs\*.py`（全模块樫扫） | 没有索引，每问一个“谁在调这个”就樫扫一遍 |
| **33** | `lvs/gui/app.py`（Get-Content 17 + Select-String 16） | 1600+ 行单文件，改一处要回看好几遍 |
| **29** | `lvs/cli.py`（含 `SS:lvs/cli.py` 12） | “加一个子命令要改 4 处”→ 每次都要重新对齐 |
| **24** | `lvs/build.py` | 同上（分片 + 字幕 + 合并都在这） |
| **20** | `lvs/tts.py` | 复用扫描 / 时长探测 / 断点 |
| 12 / 11 / 10 | `assets.py` / `publish.py` / `gui/jobs.py` | 同上 |

> 每次重读 = 至少 1 次模型调用 = **至少 9 万 input token**。上表合计约 175 次 × 9.2 万 ≈ **1,600 万 token**。

这是一个**正反馈环**：为了省 token 而写的报告，本身变成下一轮要读的东西，而且报告里又引用更多报告

> **不是说不该写报告**—— 而是说报告必须**分层**：
> 只有“给 agent 读的那一层”才能进常驻上下文，其余必须留在磁盘上“按需读”。

### F5 探针体系的固定开销

“为了拿行号，先把源码转储成 `_xxx_numbered.txt`，再分次读回来”（正是本会话的做法），单这一项就 **15 万 token**。

### F6 验证贵（时间 × 输出 × 重跑）

| 事实 | 数值 |
|---|---|

## §4 边际成本：一个动作到底多少钱

| 动作 | 模型调用 | input（按 9.2 万/次） |
|---|---|---|
| 读一个文件夹的文件列表 | 1 | ≈ 9.2 万 |
| “写探针 → 跑 → 看输出 → 改”（一轮） | 4 | ≈ **37 万** |
| 改一个模块并回归（读源码 + 改 + 跑测试 + 看失败） | 6–10 | ≈ 55–92 万 |
| 写一份中等报告（如本文） | 30–40 | ≈ **280–370 万** |
| 一次完整的“六维度审查”（规则 2） | 约 200+ | ≈ 1,800 万+ |

> 这就是为什么“只是继续往下做”会很贵：**每个动作都要重付一次“现场重建”的钱**，
> 而现场重建的价格由“常驻上下文长度”决定（9 万起），不是由任务大小决定。

```python
# 第一步：lvs/summary.py（新）—— 把 .work/tools/continuation_summary.py 的核心逻辑搬过来，强制 UTF-8
from __future__ import annotations
import sys
from pathlib import Path

def _fix_console() -> None:
    """GBK 控制台下中文不能打印（上一轮实测抛 UnicodeDecodeError）。"""
    for s in (sys.stdout, sys.stderr):
        try:
            s.reconfigure(encoding="utf-8", errors="replace")  # type: ignore[union-attr]
        except (AttributeError, ValueError):
            pass

def brief(workspace_root: Path, task: str | None = None, show_all: bool = False) -> int:
    _fix_console()
    # ……此处调用 continuation_summary 已有的聚合函数（不重写），每行一任务：
    # 任务  config  图片  门禁(开/总)  next  产物  最近
    return 0
```

### S2 ★★★ `lvs shots --peek / --index`：消灭 shots.json 常驻

**现状**：11 份 `shots.json` 共 2.71 MB（≈ 84.7 万 token）；`AGENTS.md` 只能“禁止读”（禁止本身就是缺陷）。

```python
# lvs/shots.py —— 两个读口（都不进全量 JSON）
def peek(ws, shot_id: int) -> str:
    """只打一镜：约 300 token。"""
    shots = read_shots(ws)                      # 已有函数
    s = next((x for x in shots if int(x["id"]) == shot_id), None)
    if s is None:
        return f"没有镜 {shot_id}"
    return (f"#{s['id']} {s.get('seconds', '?')}s 来源={s.get('source','?')}\n"
            f"提示词: {s.get('prompt','')}\n"
            f"旁白: {s.get('narration','')}")

def index(ws, width: int = 40) -> str:
    """一镜一行：516 KB → 约 30 KB。"""
    out = []
    for s in read_shots(ws):
        out.append(f"{s['id']:>4} {s.get('seconds', '?'):>6} {s.get('source','?'):<10} "
                   f"{(s.get('prompt') or '')[:width]}")
    return "\n".join(out)
```

**验收**：`python -m lvs shots --task UGE03 --index | Measure-Object -Line` 约 363 行（而非 516 KB）；
`--peek 193` 输出 < 400 字符。

### S4 ★★ 用“行号锚定读取”代替 numbered 转储

**现状**：为了能“按行号贴补丁”，把源码转储成 `_cli_numbered.txt` 等 8 份文件（共 481 KB ≈ **15 万 token**），再分次读回。

```python
# lvs/maptool.py（新）—— 直接输出带行号的局部，不产生中间文件
def show(path: Path, start: int, end: int, *, numbered: bool = True) -> str:
    lines = path.read_text(encoding="utf-8").splitlines()
    lo, hi = max(1, start), min(len(lines), end)
    if numbered:
        return "\n".join(f"{i:>5}| {lines[i-1]}" for i in range(lo, hi + 1))
    return "\n".join(lines[lo - 1:hi])
```

```powershell
# 替代“转储 + 分页读”的典型用法
.\.venv\Scripts\python.exe -m lvs map show lvs/cli.py 180 240   # 只拿 61 行（≈ 800 token）
.\.venv\Scripts\python.exe -m lvs map grep "add_parser" lvs/cli.py   # 只拿命中行
```

**收益**：单这一项 ≈ **15 万 token / 场会话**，而且不会在 `.work/tmp` 里堆积（磁盘与检索噪声一并消除）。

## §7 局限（请连同结论一起引用）

1. **单会话样本**：只算了本次 2 小时 53 分。与其它会话/子 agent 的对比 【信息不足】（`sessions/` 下还有 6 个 rollout 未逐一拆）。
2. **字节→token 用 3.2 B/token 粗估**（中英混合），误差 ±20%；正式数字一律用 `token_usage_record` 里的报数。
3. **缓存计价倍率 【信息不足】**：本文只报 token 计数，**不折算金额**。但“96.9% 命中缓存”这个事实本身说明：
   真正新读入只有 2.43 M token，其余是重发。
4. `function_call_output` 的序列化字节含 JSON 转义（`\n` 等），比原文大约 5%；
   因此 §2.1 的占比只用于“谁在增长”，不用于绝对体量（绝对体量用 §2.2）。
5. **工具调用数含失败重试**：本次 1,056 次里有 11 次无输出（约 1%）。
6. “重读热点”用命令字符串正则统计，**会漏掉用 `[System.IO.File]::ReadAllText` 等写法读的文件** → 该表是下界。

## §8 一句话回答“为什么这么费”

```
因为每一个小动作都要重建一次现场，
而重建现场的代价 = 常驻上下文（9 万 token）× 调用次数（本会话 845）。
下降的两个方向只有：① 把常驻面变小（S1/S2/S3/S4）；② 把调用次数变少（S4/S5/S6/S7）。
两者乘起来就是一个数量级。
```
