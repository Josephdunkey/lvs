### 0.2 方法（三类，全部只读）

1. **插桩计数**：把 `os.stat` / `pathlib.Path.iterdir` / `io.open` 换成计数包装（`_probe_perf1b/1c.py`），
   量"一次调用到底做了多少次系统调用、读了多少字节"。**不猜，只数。**
2. **黑盒计时**：直接 `time.perf_counter()` 包住真实函数（`_probe_perf2/3/5/6/7/9/11/12/15.py`），
   必要时用 `ThreadPoolExecutor` 对比并发收益。
3. **外推**：先测 20–60 镜的真值，再按 `×363/×594` 线性外推到全片，并把"每次 build 都跑"标注清楚。

### 0.3 一条重要前提

**`.work/tmp` 之外的任何文件本轮都没写。** 本轮所有探针只做读操作；
`lvs build` / `lvs voice` / `lvs assets` **没有被真正执行**（它们会改写 `shots.json`）。
因此凡"每阶段跑一次"的成本，都是**用真实子函数逐镜模拟 + 外推**得到的，不是跑完整命令的时间。

## §2 🔴 严重

### P01 `cardhtml._shoot` 的浏览器子进程没有 timeout —— 可永久挂死

**文件**：`lvs/cardhtml.py:264-286`（`subprocess.run` 在 `:282`），调用方 `render()` 在 `:289-303` 会**重试 2 次**，每次外面还套一个 `for _ in range(10): sleep(0.2)` 的"等产物落盘"循环。

**问题**：整条 graphic（图文卡片）路径依赖本机 Edge/Chrome 无头截图。
`subprocess.run(cmd, capture_output=True, text=True, errors="ignore")` **没有 `timeout=`**，而且
`capture_output=True` 把浏览器输出直接丢掉（连日志都没有）。浏览器一旦因为
"user-data-dir 被占 / 首次运行向导 / 崩溃后子进程残留"而不退出，**调用方永远等下去**。

**实测**（`_probe_perf13.py`，本机 Edge）：

```
浏览器： C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe
单张卡片栅格化 1.37s  产物 287315  err=None
19 张 graphic（UGE03）≈ 26.0s；若含重试 2 次的最坏情况 ×2
```

正常情况 1.37 s/张、19 张 26 s —— 完全可接受。**风险不在"慢"，在"没有上限"**：
进程级 hang 在 Windows 上不会自己好，`assets` 阶段的逐镜循环卡死 → 看板停在某一镜，
用户只能 Ctrl-C；而 `jobs.py` 的"停止"打的是 python 子进程树，浏览器进程未必在树里，会留孤儿。

**风险说明**：`lvs assets` 无输出、无日志、无退出的静默挂死（最坏情况：一集 300+ 镜跑了一夜没动）。
这是**资源释放 + 无超时**两个维度的叠加。

**可直接使用的修改**（替换 `_shoot` 的 subprocess 段；保留原有"查两次落盘"语义）：

```python
def _shoot(exe: str, html_text: str, out: Path, *, timeout: float = 30.0) -> None:
    """把 HTML 截成 PNG。浏览器偶尔先退出后落盘，所以查两次。

    ★ 必须带 timeout：无头浏览器在 profile 被占用 / 崩溃 / 卡在首次向导时会
      **永不退出**。原实现 `subprocess.run(cmd, ...)` 没有 timeout，
      也没有把浏览器 stderr 留下来 —— 挂死时既看不到原因、也无法自愈。
      （实测正常单张 1.37s，30s 已是 20 倍余量。）
    """
    out.unlink(missing_ok=True)
    with tempfile.TemporaryDirectory() as td:
        page = Path(td) / "card.html"
        page.write_text(html_text, encoding="utf-8")
        cmd = [
            exe,
            "--headless=new",
            "--disable-gpu",
            "--hide-scrollbars",
            "--no-first-run",
            "--no-default-browser-check",
            f"--user-data-dir={Path(td) / 'profile'}",
            f"--screenshot={out}",
            f"--window-size={W},{H}",
            page.as_uri(),
        ]
        try:
            proc = subprocess.run(
                cmd, capture_output=True, text=True, errors="ignore", timeout=timeout,
            )
        except subprocess.TimeoutExpired:
            print(f"  ✗ 浏览器截图超时（{timeout:.0f}s）：{out.name} —— 跳过这张卡片")
            return
        except OSError as exc:
            print(f"  ✗ 浏览器启动失败（{exe}）：{exc}")
            return
        if proc.returncode != 0:
            tail = (proc.stderr or "").strip().splitlines()[-3:]
            print("  ⚠ 浏览器返回非 0：" + " / ".join(tail))
        for _ in range(10):
            if out.is_file() and out.stat().st_size > 0:
                return
            time.sleep(0.2)
```

另外把 `render()` 的两次尝试改成"每次 attempt 也有预算"（避免 2×30 s 叠加成 60 s 以上无提示）：

```python

    out_path.parent.mkdir(parents=True, exist_ok=True)
    page = html_for(card)

        if out_path.is_file() and out_path.stat().st_size > 0:

```

### P02 `lvs voice` 复用扫描：每镜 2 次 ffmpeg 进程 + 读同一 json 两遍

**文件**：`lvs/tts.py:731`（第一次 `ff_duration(out)`）与 `lvs/tts.py:823`（第二次 `ff_duration(out)`）；
另外 `lvs/tts.py:695 _existing_boundaries` 与 `lvs/tts.py:710 _audio_meta` **读的是同一个**
`audio/shot-NNN.json`，在 `run_command` 的跳过分支里被读了两遍。

**问题**：`_audio_reusable()` 返回 `bool`，把"这个音频多长"这个**已经测出来的数据丢掉了**；
调用方拿到 `True` 之后又调一次 `ff_duration(out)` 写进 `shot["audio_duration"]`。
本机 ffprobe 缺失，`ff_duration()` 走 `ffmpeg -i` + 正则解析 stderr：**实测 0.21 s（热）～0.59 s（冷）**。

**实测**（`_probe_perf3.py`，只读模拟，未写任何文件）：

```
== C. 模拟 voice 的复用扫描（读 30 镜，外推到 363） ==
   30 镜：20.86s（其中 ffprobe 0 次 = 2 × 可复用镜数）→ 外推 363 镜 ≈ 252.4s（0 次进程启动）
```

> 说明：那行"0 次"是我探针里的整数除法写错了（`probes // len(order) * 363`）。真实次数是
> **2 × 可复用镜数 = 2 × 363 = 726 次进程启动**，时间 20.86 s/30 镜是准的。

**风险说明**：`lvs voice` 在一次"完全没改讲稿"的续跑里，**4.2 分钟一个字都没合成**（UGE04 594 镜更久）。
这跟主报告 §8 里"续跑费 token"是同一个病根：**每轮都从头把已知信息重新测一遍**。

**可直接使用的修改**：

```python
def _audio_reusable(
    ws: Workspace, sid: int, out: Path, voice: str, narration: str
) -> float | None:
    """已有音频能否复用。可复用则返回**它的时长**，否则返回 None。

    ★ 返回类型从 `bool` 改成 `float | None`：`ff_duration(out)` 本来就要跑，
      结果是调用方紧接着需要的东西。原实现返回 True 之后，调用方在
      `run_command` 里又 `ff_duration(out)` 测了一遍 —— 363 镜白白多起
      363 个 ffmpeg 进程（实测 0.21–0.59 s/次）。

    只看"文件存在"是不够的（票据 47）：`--force` 重合成**失败时不会删掉旧文件**，
    下一轮就把它当成功产物跳过 —— 旧音色、旧文本的音频于是留在片子里。
    """
    if not (out.is_file() and out.stat().st_size > 0):
        return None
    dur = ff_duration(out)
    if not dur:
        return None
    meta = _audio_meta(ws, sid)
    if meta is None:
        return None
    if str(meta.get("voice") or "") != str(voice):
        return None
    digest = meta.get("text_sha1")
    if digest and digest != _text_sha1(narration):
        return None
    return dur
```

顺手把"同一 json 读两遍"合并（`_audio_meta` 已经把它解析出来了）：

```python
def _boundaries_from_meta(meta: dict[str, Any] | None) -> list[Boundary] | None:
    """从已解析的 audio/shot-NNN.json 里取词边界（避免为同一文件再读一遍盘）。"""
    if not meta:
        return None
    bounds = meta.get("boundaries")
    if not isinstance(bounds, list):
        return None
    return [Boundary(b["offset"], b["duration"], b["text"]) for b in bounds]
```

然后跳过分支里 `bounds = _boundaries_from_meta(meta)`（`_audio_reusable` 可以改成回传 `(dur, meta)`，
或把 `_audio_meta` 提到调用方读一次再传进去 —— 两种都行，关键是**别读两遍**）。

```python
    """可复用时必须回传时长，且**只探测一次**（否则 363 镜多起 363 个进程）。"""
```

## §3 🟠 一般（每次运行稳定浪费数十秒 / 随规模线性恶化）

### P03 `lvs build` 复用扫描：逐镜 ffprobe

**文件**：`lvs/build.py:425`

```python
        seg_dur = (ff_duration(dst) or 0.0) if dst.is_file() else 0.0
```

**问题**：`_segment_reusable()` 需要"盘上这段现在多长"来判断要不要重渲。
于是**每个镜都得起一个媒体探测进程** —— 即使这 363 个片段一个都不会变。

**实测**（`_probe_perf7.py` / `_probe_perf8.py`，同一个 `UGE03`）：

```
ffmpeg.duration(dst)  平均 0.5437s → 363 镜 197.4s
_asset_content_fp(src) 平均 0.0004s → 363 镜 0.2s        ← 哈希根本不是瓶颈
排序段目录 glob 平均 0.0017s  → 363 镜 0.6s
复用扫描合计 0.5458s/镜 → 363 镜 ≈ 3.3 分钟（每次 build 都跑）

同一文件 shot-001.mp4 ×10：平均 0.2328s（min 0.2017 max 0.3952）
十个不同文件 各一次：平均 0.5939s（min 0.2135 max 0.7973）
裸 ffmpeg -i 十个不同文件：平均 0.1792s
```

**结论**：**同一文件热读 0.23 s，换文件冷读 0.59 s** —— 差在 Windows 上进程每次重新打开
158 MB 目录里的新文件（含 Defender 扫描）。363 镜 = **1.4–3.6 分钟**，且每次 `lvs build` 都跑，
哪怕你只是想看看有没有漏镜。

**风险说明**：这不是"慢一点"，而是"续跑成本恒定且不可跳过"。它还会掩盖真正的耗时
（渲染 vs 探测混在一起），让人误判"build 要跑一小时"。

**可直接使用的修改 A（推荐 · 零语义变更 · 只把探测并发起来）**：

在 `build_segments()` 的 `for idx, shot in enumerate(...)` **之前**加一段预热：

```python
    # ★ 逐镜探测并发化：`_segment_reusable` 需要"盘上现在多长"，
```

### P04 `ffmpeg.tools()` 没有缓存 —— 每次探测/渲染都重解析一遍可执行文件路径

**文件**：`lvs/ffmpeg.py:67-79`，被 `probe()`（`:133`）、`duration()`（`:149`）、
`_run_filter()`（`:190`）、`run()` 的调用方反复调用。

```python
def tools() -> tuple[str, str]:
    ffmpeg = shutil.which("ffmpeg") or _local_binary("ffmpeg.exe") or _imageio_ffmpeg()
    ffprobe = shutil.which("ffprobe") or _local_binary("ffprobe.exe") or ""
```

**问题**：`shutil.which()` 要遍历 `PATH` 的每个目录（本机 `PATH` 很长），
`imageio_ffmpeg.get_ffmpeg_exe()` 更要在 site-packages 里找。这些结果**在进程生命周期内不会变**。

**实测**（`_probe_perf2/3.py`）：

```
   shutil.which('ffmpeg')     0.0286s
   shutil.which('ffprobe')    0.0308s
   get_ffmpeg_exe()           0.1198s（首次；之后被 imageio 自己缓存，≈0.02s）
   ffmpeg.tools()（合计）      0.0556s  ← 每次 probe/duration/run 都走一遍
   ffmpeg.duration()           0.2140s  ← 含上面那次 tools()
```

**风险说明**：一次 `lvs build` + `lvs voice` 的"复用扫描"要调 700+ 次 `duration()`，
即 **700+ 次 `tools()` ≈ 22–44 秒**纯粹用来"再找一遍 ffmpeg 在哪"。
`_finalize` 的一次全片重编码则不受影响（它只在开头调一次 `tools()`）。

**可直接使用的修改**（`lvs/ffmpeg.py`，删掉原 `tools` 函数体换成下面这份）：

```python
from functools import lru_cache


@lru_cache(maxsize=1)
def tools() -> tuple[str, str]:
    """返回 (ffmpeg, ffprobe)。ffprobe 可能为空串（调用方需容忍）。

    ★ 结果必须缓存：`probe` / `duration` / `_run_filter` 每次都调它，而它每次
      都跑 `shutil.which`×2（+ `imageio_ffmpeg.get_ffmpeg_exe()`）——
      实测 0.0556s/次；一次 build+voice 的逐镜探测会调 700+ 次，
      白白烧掉 20–40 秒。
    路径在进程内不会变；`lvs doctor` 与真正启动子进程仍用真实字符串，
    所以缓存只影响"找路径"这一步。若用户中途装了 ffmpeg，
    新开一个进程即可生效（GUI 的每次运行本来就是新子进程）。
    """
    ffmpeg = shutil.which("ffmpeg") or _local_binary("ffmpeg.exe") or _imageio_ffmpeg()
    ffprobe = shutil.which("ffprobe") or _local_binary("ffprobe.exe") or ""
    if not ffmpeg:
        raise FFmpegError(
            "未找到 ffmpeg（`lvs build` / `lvs voice` 必需）。\n"
            "  A) 推荐：pip install imageio-ffmpeg（本项目的 venv 已内置）\n"
            "  B) 系统安装：winget install Gyan.FFmpeg（装完重开终端）\n"
            "  C) 或下载 https://www.gyan.dev/ffmpeg/builds/ 的 release-essentials，"
            "把 bin 目录加入 PATH。装好后用 `lvs doctor` 复检。"
        )
    return ffmpeg, ffprobe
```

注意：`lru_cache` **不缓存异常**，所以"没装 ffmpeg"时照样每次都报同样的错（不改行为）。
需要强制刷新时用 `tools.cache_clear()`（写进 docstring 即可，代码与测试都不必依赖它）。

**守卫测试**：


**风险说明**：**≈2.5 ms/行**。这个开销发生在读取子进程 stdout 的线程里
（`jobs.py:360` 的 `for line in proc.stdout`），**会直接拖慢正在跑的阶段**，
而长任务最常见的行数正是几千行量级。Windows 上每次 open/close 都要过一遍
文件系统过滤驱动（Defender 等），所以比 POSIX 贵得多。

**可直接使用的修改**：把句柄在 `Job` 生命周期内保持住（`__init__` / `_run` 各一处）：

```python
    #: 日志落盘的**常开句柄**。逐行 open/close 实测 2.5ms/行（Windows + Defender），
    #: 而这个开销压在读子进程 stdout 的线程上，会拖慢正在跑的阶段。
    _sink_fh: Any = None

    def _open_sink(self, path: Path) -> None:
        try:
            path.parent.mkdir(parents=True, exist_ok=True)
            self._sink_fh = path.open("a", encoding="utf-8", buffering=1)  # 行缓冲
            self.sink = path
        except OSError:
            self._sink_fh = None
            self.sink = None

    def _close_sink(self) -> None:
        fh, self._sink_fh = self._sink_fh, None
        if fh is not None:
            try:
                fh.close()
            except OSError:
                pass

    def emit(self, text: str) -> None:
        with self._lock:
            seq = self._seq
            self._seq += 1
            self._lines.append((seq, text))
            subs = list(self._subs)
            fh = self._sink_fh
        for q in subs:
            q.put((seq, text))
        if fh is not None:
            try:
                fh.write(text + "\n")
            except (OSError, ValueError):
                self._sink_fh = None      # 写不进就放弃落盘，别让日志拖垮任务
```

并在 `JobRegistry._retire()` 的 `job._finish(returncode)` 之后调 `job._close_sink()`
（父进程里也要在异常路径 `finally` 关，避免 Windows 上文件被占着删不掉）。

```python
def black_ratio_sampled(
    path: Path, *, windows: int = 6, window: float = 20.0,
    threshold: float = 0.10, min_duration: float = 0.5,
) -> float | None:
    """抽样版黑屏占比：只在片头/中段/片尾取若干 20s 窗口逐帧看。
    ★ 为什么：`blackdetect` 要**逐帧解码整片**，实测 0.108s/秒画面 ——
      1411s 的片子就是 2.5 分钟/次 build。而这一步的目的只是"发现整片黑掉"
      这类灾难性故障，抽样完全够用；真要逐帧严格检查，那是 `lvs qc` 的活。
    """
    total = duration(path)
    if not total or total <= 0:
        return None
    # 均匀取 windows 个窗口，避开片尾（片尾可能有正常的黑场过渡）
    step = max(0.0, (total - window) / max(1, windows - 1)) if total > window else 0.0
    spans = 0.0
    covered = 0.0
    for i in range(windows):
        ss = min(step * i, max(0.0, total - window))
        text = _run_filter(
            path,
            ["-ss", f"{ss:.3f}", "-t", f"{window:.3f}",
             "-vf", f"blackdetect=d={min_duration}:pix_th={threshold}", "-an"],
        )
        covered += min(window, total - ss)
        spans += sum(float(x) for x in _RE_BLACK.findall(text))
    if covered <= 0:
        return None
    return min(1.0, spans / covered)
```

然后在 `final_sanity` 里换成它（并对 `video-track.mp4` 的 mtime 做一次性记忆，
同一产物不重复检；`record_timing` 已有地方放这个结论）：

```python

```

**收益**：2.5 分钟 → 约 **12 秒**（6 × 20 s 窗口 ≈ 120 s 画面 × 0.108 s）。

```python
        low = kw.lower()
        if len(low) >= 2:
            substrings.append(low)
    return kw_tokens, substrings


def _score_with(entry: dict[str, Any] | Entry, kw_tokens: set[str], substrings: list[str]) -> int:
    tags = set(entry.tags if isinstance(entry, Entry) else entry.get("tags", []))
    path = (entry.path if isinstance(entry, Entry) else entry.get("path", "")).lower()
    return 2 * len(kw_tokens & tags) + sum(1 for s in substrings if s in path)


def score_entry(entry: dict[str, Any] | Entry, keywords: Iterable[str]) -> int:
    """加权重合度：词元交集 ×2 + 关键词在路径中的子串命中 ×1。（单条 API，保持原签名）"""
    return _score_with(entry, *_query_of(keywords))


def search(
    index: dict[str, Any], keywords: Iterable[str], min_score: int = 1
) -> list[tuple[dict[str, Any], int]]:
    """返回按分数降序的 (entry, score)，仅含 score ≥ min_score。

    ★ 关键词分词只在**进入循环前**做一次。原实现把它放在 score_entry 里，
      等于对同 5 个关键词分词 N 次：实测 N=20000 时 100,000 次 tokens()，
      占 search() 全程的 1/3；提出来 0.097s → 0.020s（-79%）。
    """
    kw_tokens, substrings = _query_of(keywords)
    scored: list[tuple[dict[str, Any], int]] = []
    for entry in index.get("entries", []):
        s = _score_with(entry, kw_tokens, substrings)
        if s >= min_score:
            scored.append((entry, s))
    scored.sort(key=lambda pair: (-pair[1], pair[0]["path"]))
    return scored
```

**顺带一条**：`assets.py:857` 与 `:911` 在 `source=library` + `mode=auto` 且未命中时
会**对同一镜扫两遍**全表。若采纳上面的改法，把两处合并成一次 `search()` 取
`scored[0]` 即可（`best_match` 目前内部就是 `search()` 取第一条，等于把整张表排完序只为拿最大值）。

**守卫测试**（等价性最重要）：

### P12 `zoompan supersample=2` 是渲染的真瓶颈（比编码贵 3 倍）

**文件**：`lvs/build.py:227-275`（`kenburns_filter`），配置项 `build.kenburns_supersample`（默认 2）。

**实测**（`_probe_perf6.py`，同一个 3 s / 1080p / 真实素材）：

```

preset=veryfast ss=2 crf=20          2.99s    908.5 KB
preset=medium   ss=1 crf=20          1.18s   1194.8 KB     ← 3.2×
preset=veryfast ss=1 crf=20          0.70s    876.2 KB     ← 5.4×
preset=veryfast ss=1 crf=23          0.68s    574.4 KB
```

**判断**：`supersample=2` 的 3.2× 代价是**故意的**——`build.py:232-234` 的注释解释了：
zoompan 取整会让推近变成"卡住几帧、跳 1 像素"，在 2× 分辨率上算再 lanczos 降回
可以把量化误差压到亚像素（帧间差异变异系数 0.2034 → 0.1191）。
**这是画质换时间，不该我一句话替你改。** 但要给用户一个明确的旋钮与数字：

- 现状：363 镜 × 3.55 s ≈ **21.5 分钟**（本任务 3 s 镜长实测算）；
  按平均镜长 3.89 s 外推 ≈ **27.8 分钟**。
- `supersample = 1`：约 **7–9 分钟**（-70%），代价是慢速推近可能有轻微台阶感。
- 若只在**大幅运镜**（pan）时用 supersample=2、其余用 1，收益接近前者（需要按 `motion_sequence` 逐镜决定）。

**建议**：不改默认值，只在 `build` 收尾打印一行"渲染 N 个片段用了 X 分钟；
若想换速度，`build.kenburns_supersample = 1` 可省约 70%，请目测对比"。
（`record_timing()` 已经在记 `last_seconds`，直接拿它可以算。）

### P13 并发渲染：收益有限 —— **这条明确建议不要做**

**实测**（`_probe_perf5.py`，4 个 3 s 片段，同参数）：

```
串行 14.19s（单个平均 3.55s）
2 线程 12.27s → 加速 1.16x
4 线程 10.62s → 加速 1.34x
```

**结论（反面清单）**：x264 单进程已经吃满 20 个逻辑线程（`ffmpeg` 默认按核数开 frame threads），
所以"多开几个 ffmpeg 并行渲染"最多 1.34×，却要付出：内存峰值 ×N（每进程 1080p 缓冲）、
与 GPU 侧服务抢 CPU/磁盘、日志交错难读、失败重试语义复杂化。
**用并发**：只用在**探测类**工作（P03 的 `duration()`，实测 4.6×，因为那是在等进程启动，不是算）。
**别用在**：渲染、生图、TTS。

## §7 架构改进建议（性能视角）

### A. 加一层「逐镜元数据侧车」——把重复探测一次性消掉

P02 / P03 / P07 / P09 是**同一个病**：**每轮都重新"测量"上一轮已经知道的事情**。

现状已经有半个答案：`lvs/assets.py` 的 `_src_record`（`_file_digest` + `_request_key`）
和 `build` 的 `.segkeys.json`（真名；`segment_key`）都在做"指纹 → 决定要不要重做"。
缺的是把这些指纹**和它的测量结果绑在一起**：

```
.work/<task>/.meta/
├── assets.json   {shot-001: {src, src_size, src_mtime_ns, src_sha1, req_key}}
├── audio.json    {shot-001: {wav_size, wav_mtime_ns, duration, voice, text_sha1}}
└── segments.json {shot-001: {mp4_size, mp4_mtime_ns, duration, want_key, placeholder}}
```

**规则**：`size + mtime_ns` 一致 ⇒ 文件没被外部动过 ⇒ 直接信注册表里的
`duration`，**不起进程**；不一致 ⇒ 探测一次并回写。
这一条把"探测"从"每轮 O(镜数) 次进程启动"降到"只在真变化时发生"，
同时**保留** `assert_segment_rendered()` 的防线（越界的伪造仍然会被 size/mtime 不一致抓到）。

### B. `lvs/ffmpeg.py` 升级为「进程代理层」

目前 27 处调用点各自拼参数（有的带 `-hide_banner -nostats`，有的不带；有的自己 `subprocess.run`）。
建议收敛成三个入口：`probe()` / `run()` / `run_many()`（唯一并发入口，内部 8 线程）。
好处：`tools()` 缓存、超时、`-nostats`、错误消息格式**只有一份**；
`run_many()` 让"翻 363 个文件"这类需求不必再被写成串行 for。

### C. 读模型与写模型分离（GUI）

`gui/store.py` 现在是"实时扫盘"的读模型：每次刷新都重新数一遍目录。
而 manifest 里**已经有** `stages.<stage>.{done,total}`（`mark_stage_progress` 就是干这个的）。
建议列表页只读 manifest 快照（一次 stat + 一次 json），
把"目录里真有几百个文件"这类校验降级为**点击进任务页时才做**（任务页只有 1 个任务，
代价 = 现在的 1/12）。这样 `list_tasks()` 就从 O(任务数 × 镜数) 变成 O(任务数)。

### D. 显式化的"分阶段预算"

`record_timing()` 已经在记 `last_seconds`，但只在 manifest 里。
建议 `lvs build` / `lvs voice` 收尾打印一张表：

```
本轮耗时：探测 2m58s ｜ 渲染 21m12s ｜ 终检 2m30s ｜ 混流 4m52s
（探测 2m58s 中 0 个片段发生变化 —— 若想省掉，见 docs/性能-2026-10-05.md P03）
```

这是**唯一能让人不误判"这项目就是慢"**的手段：把"白花的钱"和"真花的钱"分开显示。
