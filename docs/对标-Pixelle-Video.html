对标 Pixelle-Video：是不是重复造轮子

2026-10-03。这一份尽量只用核实过的事实—— 你那一侧全部以代码为准（本项目纪律："我们缺什么必须用代码核实，不能凭印象"）， Pixelle 那一侧以它的 README + 官方文档 + 第三方拆解为准。

一、先把 Pixelle 说准

项 事实
出身 阿里巴巴 AIDC-AI（2026 年组织更名 ATH-MaaS，旧链接自动转址），Apache 2.0
定位 AI 全自动短视频引擎——"输入主题 → 成片"，官方宣传场景是"日更 50 条"的矩阵号 / 跨境电商 / 知识付费
管线 文案生成 → 配图规划 → 逐帧处理 → 视频合成
门面 Streamlit Web UI（三栏：内容 / 语音 / 视觉），历史记录、批量任务、实时进度、成片预览
模板 templates/ 按分辨率分三类（1080×1920 / 1920×1080 / 1080×1080），文件名前缀 static_ / image_ / video_ 表示"纯文字 / AI 图背景 / AI 视频背景"，都是 HTML，可直接改
生图 / 生视频 三条路：本地 ComfyUI、云端 RunningHub（48G 机器）、直连 API（DashScope / OpenAI / Seedream / Seedance / Kling）

扩展形态 数字人口播、动作迁移（上传参考视频+图）、图生视频（WAN 2.1 等）

成本档 免费档 = 本地 Ollama + 本地 ComfyUI；云端档 = 通义 + RunningHub

一句话：Pixelle 是门槛最低、吞吐优先的通用短视频装配线。

三、重叠的部分（诚实说，这部分你确实在重造）

骨架是同一条：

文案 → 分镜 → 配图(ComfyUI) → TTS → ffmpeg 合成

这条链 Pixelle 做得比你成熟，而且它有三件你完全没有的通用件：

它有你没有（且这是通用件，不是它的特色） 你的现状
BGM 背景音乐 ❌ 代码里没有（只在文档提过）——讲书视频没有 BGM，氛围差一截
整片版式模板（HTML 模板库、按分辨率分类） ⚠️ 你有 cardhtml，但只做 graphic 卡片，不做"整片版式"
直连 API 生图/生视频 ❌ 只有 ComfyUI。没显卡就没法出图
数字人 / 动作迁移 / 图生视频 ❌ 全无（形态扩展）
REST API + Python SDK ❌ 无（批量与外部调用没法程序化）
Docker / 一键整合包 ❌ 无（自用没问题，给别人就是门槛）
云端显卡（RunningHub） ❌ 无（8G 本机是硬约束）

所以"重复造轮子"的指控，在骨架这一层是成立的。

四、不重叠的部分（这三件事 Pixelle 结构性地不做）

① 人审门禁 —— 它面向的形态不需要，你面向的形态必须要有

Pixelle 的用法是"点一下 → 等 3–10 分钟 → 看片"。失败了重跑，成本 5 分钟。 你的用法是"几百镜 → 跑几小时 → 479 张图"（这是你自己踩过的：跑完 10 小时才发现整批提示词是旧版）。错一次全废。

所以你把工程力气花在"验证"这一层（G0–G5 / 指纹绑定 / qc / 契约 / 熔断）， Pixelle 花在"交互"这一层（Web UI / 模板 / 一键包）。

用你记忆里那条判据来看：多 agent 领域的失败分布是 系统设计 41.77% / 交互错位 36.94% / 任务验证 21.30%。 Pixelle 赌的是"交互错位"是主要矛盾，你赌的是"任务验证"。 两个赌注都对——只是对不同长度的视频。

② 人物视觉一致性 —— 它走的是另一条路线

Pixelle 有音频克隆、有数字人口播（固定人物图 + 驱动）， 但它没有"同一个人在几百个不同分镜里保持同一张脸"这条链——那是静态分镜长视频的刚需。

你用定妆锚定解决它：L1 文字锚定（9 条 lint 判据）+ L2 参考图 img2img。 这是你真正的技术差异化，而且今天刚从"半接线"补成真能跑。

③ 内容方法论 —— 这层它完全没有

Pixelle 是"主题 → LLM 生成文案"，通用、快、但不讲究。 你是"一本书 → 拍摄稿（有格式契约）→ 分镜"， 外面还挂着 7 个讲书技能（木鱼水心/萧包子文风、文学理论工具箱、黑白漫画分镜…）。

这是"内容"与"工具"的分工：Pixelle 提供装配线，你提供"讲什么、怎么讲"。

五、结论

是重复造轮子吗？——骨架是，灵魂不是。

判断
文案→分镜→配图→TTS→合成 这条骨架 确实重复。Pixelle 更成熟，且免费、开源、能直接用。
人审门禁 + 人物一致性 + 内容方法论 不重复。这三件互为因果：因为"书讲成长视频"才需要一致性；因为几百镜成本高才需要门禁。

更准确的说法：你不是在重造 Pixelle，你是用同一根骨架做一件 Pixelle 不做的事。 但只要你不承认骨架重叠，就会在"BGM / 模板 / Web UI 门面"这些地方重复劳动—— 而这些恰恰是可以借、不必自造的。

六、★ 一个必须点出来的隐患：你的差异化能力，在你自己的 GUI 里点不到

我查了 lvs/gui/*.py（1640 行 / 20 路由）：

grep -rlE "gate|qc|cast" lvs/gui/*.py   →  零命中

GUI 能做的事：任务管理、逐镜编辑、运行/停止、进度流、素材库、体检、缩略图。 但它不含门禁、不含巡检、不含定妆。

也就是说：你最强的三件事，只有命令行能用。 这跟项目自己记录在案的遗留项一致（"门禁只在 lvs run 与命令行生效：lvs studio / lvs gui 还没走门禁账本"）。

对比之下 Pixelle 的 Web UI 是它的主入口，配置→生成→预览一条龙。

这比"缺 BGM"严重得多 —— 因为它意味着你在维护两个世界： 命令行里的严肃流水线，和 GUI 里的轻量播放器。

七、如果只做三件事

优先 做什么 为什么
1 把门禁/巡检/定妆接进 GUI 消掉"两个世界"。这是自用效率问题，不是给别人看的问题
2 加 BGM（最便宜的通用件） 代码里完全没有，而讲书视频缺 BGM 很影响成片观感。Pixelle 有现成做法可抄
3 别碰数字人/动作迁移/直连 API 那是 Pixelle 的形态扩展，与"讲书长视频"无关；做了就是真·重复造轮子
