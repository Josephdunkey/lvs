# 架构审查 · 整体（2026-10-03 第三轮）

> 范围：**整个项目的架构**，不只是某一处流程。方法是"先量化审计 → 再联网核查同类项目 →
> 只改最高价值且可验证的部分"，最后把约束写成测试钉住。

---

## 一、审计方法

不靠读代码的"感觉"，先出数字：

| 手段 | 结果 |
|---|---|
| 模块规模 | 28 个模块 / 14.6k 行；最大 `cast.py` **1497 行**，`tts.py` 830、`shots.py` 820、`assets.py` 796 |
| import 图（AST 解析） | **无环依赖**；`config`（17 个依赖者）与 `workspace`（10）是事实上的 core |
| 出度分析 | 各阶段模块出度都 ≤4 —— 耦合不重，说明问题不在"互相缠" |
| 函数内延迟导入 | **大量**（`cast`/`migrate`/`qc` 等都在函数体里 `from lvs import …`） |
| 阶段定义扫描 | ★ **同一份"阶段"信息散落 6 处** |
| `argparse.Namespace` 扫描 | ★ **2 处伪造**（`run.py` / `studio.py`） |
| 错误类盘点 | 16 个，**无共同祖先**；退出码 `0/1/2/3` 在 110 处直接写数字 |
| 签名/指纹实现扫描 | ★ 同一段 `join→sha1→截断` **字面重复 3 遍** |

**结论**：耦合不重，但**"同一个概念没有单一真源"**是全局性的毛病。
它不表现为"改不动"，表现为**改漏了不报错** —— 这才是这类项目最贵的故障形态。

## 二、六类缺陷（按危害排序）

### ★ D1 · 阶段定义散落 6 处（最严重）

"有哪些阶段、每个阶段认哪些参数、产物是什么、被哪道门守"这件事：

| # | 位置 | 写的是 |
|---|---|---|
| 1 | `cli.py` | 每个阶段的 argparse 参数与位置参数 |
| 2 | `gui/jobs.py` | `STAGE_SPEC` + `STAGE_POSITIONAL`（**参数表抄了第二遍**） |
| 3 | `run.py` | 硬编码顺序 + 逐阶段手写 kwargs |
| 4 | `studio.py` | 再写一遍调用 |
| 5 | `pipeline.py` | `GATE.stage` 字符串 |
| 6 | `workspace.py` / `board.py` | `is_stage_done(stage)` / `STAGE_ORDER` |

`gui/jobs.py` 里甚至写着注释"**与 cli.py 的子命令参数一一对应，不许出现这里没有的东西**" ——
作者知道这件事，但没有真源可依，只能靠注释提醒。

**危害是静默的**：改一个 CLI 参数名 → 编排器 `getattr(args, "旧名", None)` 拿到 `None`
→ 那个开关被悄悄忽略 → 跑完才发现"我明明加了 `--no-llm`"。

**改法**：`lvs/stage.py` 成为单一真源（顺序 / 标题 / 短名 / 位置参数 / 开关表 / 门禁 / 产物 / 依赖），
其余各处读它。CLI 保留手写 parser（它还要管 `--demo` 这类 CLI 专属开关与帮助文本），
但由**契约测试**保证不漂移。

### ★ D2 · 编排器伪造 `argparse.Namespace`（把 CLI 的形状渗进核心）

`run.py` 与 `studio.py` 各自造 `argparse.Namespace` 去调 `run_command(config, ws, args)`。
后果：**阶段无法在程序内组合**（要么有 args 要么没有），且字段名写错只会静默失效。

**改法**：`StageContext`（`config` / `ws` / `options` / `force`）成为编排层与阶段之间的接口；
`options → Namespace` 的适配**收敛到一处**（`StageContext.as_namespace`，标注为过渡期设施）。
架构测试断言"全仓只有这一处构造 Namespace"。

### ★ D3 · 没有产物血缘 → 上游改了不知道

只记 `outputs` 不记 `inputs`，于是：**重新 `parse` 之后 `shots` 仍被判为已完成，拿旧解析结果继续跑** ——
全程不报错。这是实测确认过的真 bug，不是理论风险。

**改法**：`mark_stage(inputs=…)` 记下上游产物当时的签名；`is_stage_done` 改为
"产物齐全 **且** 上游未变"（`stale_reason()` 给出人话原因）。
这是 Dagster 的 **Software-Defined Asset** 思路：编排以**产物**为中心，
`is it stale?` 由数据回答，而不是由人记得删文件。

> 兼容：老 manifest 没有 `inputs` 字段 → 不判失效（行为与从前一致）。

### D4 · 错误处理无共同祖先，退出码靠记

16 个 `*Error` 各自继承 `RuntimeError`/`Exception`/`KeyError`。上层想说
"这是输入问题、别重试"只能 `except A, B, C, …` 地枚举 —— **加一个新错误类就漏一个**。

**改法**：`lvs/errors.py` 定义 `LvsError` + 四个语义退出码：
`0 成功 / 1 有失败件 / 2 输入配置不对（改了再来）/ 3 被人审门禁拦住（等人决定，不是错误）`。
既有错误类改**多重继承**（`class AssetError(LvsError, RuntimeError)`）——
`except AssetError` / `except RuntimeError` / `except LvsError` 全都能用，零破坏。

**`2` 与 `3` 分开是关键**：混在一起，自动化脚本就没法区分"该等人批准"和"该报警"。

### D5 · 同一个"求签名"写了三遍

`build._segment_key` / `assets._request_key` / `library._signature` ——
字面上都是 `join → sha1 → 截断`，但三份**各自演化过**（用 `|` 还是 `\x1f`、截 16 位还是不截）。
本项目在"同一件事写两遍"上吃过多次亏（否定式规则、次数统计口径）。

**改法**：`lvs/artifact.py` 提供 `signature()`（参数签名）与 `fingerprint()`（文件集指纹），
把三处统一过去；**内容哈希**（`assets._file_digest` 真读字节，有意更严格）保留，
并写进测试的**显式白名单 + 理由**。

### D6 · God modules（只记录，未动）

`cast.py` **1497 行**（lint + 库 IO + 提示词 + 渲染 + 审阅表 + CLI 全在一个文件）；
`tts.py` 830 / `shots.py` 820 / `assets.py` 796。

这是"按命令切文件"而不是"按职责切"的结果。**本轮没动** —— 理由是：
它的收益是"文件变小"（可读性），风险是触碰 800+ 个测试覆盖的核心逻辑，
而**当前没有因此产生故障**。已列入待办（见 §六）。

## 三、联网核查：同类项目怎么做的

| 来源 | 关键做法 | 本项目采纳 |
|---|---|---|
| **Dagster** | **Software-Defined Assets**：编排围绕**产物**而非任务；`is it stale?` 由数据回答；**官方明确建议"业务逻辑与环境细节分离"（I/O Managers）** | ✅ D3（产物血缘 + stale）+ D2（核心与 CLI 分离） |
| **Pixelle-Video**（AIDC-AI，5k★） | `pipelines/base.py` 抽象基类 + **模板方法**（八步骨架在基类，每步可覆盖）；`services/` 与 `pipelines/` 分层 | ✅ D1（阶段表即"骨架"）+ 分层方向（`artifact`/`errors` 在下，`stage` 在中，`cli` 在上） |
| **VidForge** | 每个节点有**稳定契约**；provider 操作记 request hash + attempt；**resume 不重放已完成节点** | ✅ D3（血缘判"该不该重放"） |
| **Etherlabs multimodal-video-pipeline** | 场景图 durable；**failure 是一等状态**；批准**绑定版本 + checksum** | ✅ 已有（门禁指纹绑定）+ D4（`Blocked` 与 `Failed` 分成不同的码） |
| **Inngest / RepoClip** | `step.run()` **步骤级隔离重试与日志** | ⏳ 待办（见 §六，本项目目前只有逐镜隔离） |
| **DAG 设计原则** | 幂等 / 小原子任务 / **边界有数据契约** / inline tests | ✅ 门禁即"边界契约"；D3 让"幂等"有了判据 |

**一句话**：主流做法都在把"流水线的形状"从代码里抽出来、变成**可检查的数据**，
并让**失效与状态由数据回答**而不是由人的记忆回答。本轮的 D1–D5 都在做这件事。

## 五、验证

**架构测试 24 条全绿**，而且它们在写的过程中**当场抓出 5 个真问题**：

| # | 抓到的 | 说明 |
|---|---|---|
| 1 | `board.py` 藏着**第 6 份**阶段顺序副本 | 第一版判据只查了 `run.py` 里的那个字面量 → 教训：判据要按**形状**写，不能按"某一个已知写法"写 |
| 2 | `assets` 被 **G1 + G2 两道门**守，而阶段表写成了单值 | 单值字段表达不了 → 改成 `gates: tuple` |
| 3 | `gui/jobs.JobError` 没继承统一基类 | — |
| 4 | `tts.py` 自己做了一份参数签名 | — |
| 5 | `library.py` / `build.py` / `assets.py` 三处签名重复 | 抽 `artifact.signature` 统一 |

**顺带补上一个"文档当愿望用"的坑**：`run.py` 的 docstring 里写着
"用 `--keep-going` 时不因单阶段失败而中断"，但**这个开关既没实装也没有 CLI 参数**。
本轮实装，并明确了语义边界：**`--keep-going` 只跳过"失败件"，不跳过"人审门禁"** ——
门禁跳过去就等于放弃人审，而那正是这套流水线存在的理由。
三条测试钉住：失败时继续 / 默认遇错即停 / **门禁拦住时 `--keep-going` 也停**。

**真机验证**（不是 mock）：

```
lvs run --task NW01P1          → 仍在 G0 正确停下，提示与改造前逐字一致
产物血缘：改 parse.json        → shots 自动判为「上游产物已变：parse.json」（原来是不报错）
         老 manifest（无 inputs）→ 行为不变（向后兼容）
lvs gate / lvs styles / 各阶段 → 正常
全仓 argparse.Namespace 扫描   → 只剩 stage.py 一处
```

**回归**：**502 passed / 0 failed**（四组：132 + 200 + 81 + 89），改动文件 `pyflakes` 零告警。

**`test_workspace` / `test_resume` 在本环境跑不完**（不是失败，是每次临时目录拆除卡住）：
栈落在 **native** `shutil._rmtree_unsafe`，此时 shim 已被 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 关掉 ——
即问题在文件系统层，与代码无关。改用**等价验证**覆盖了这两个文件里与本轮改动相关的全部语义：
**16/16 通过**（含新增的产物血缘、向后兼容、`write_shots` 落盘格式、损坏 json 处理）。

> ⚠ **本环境的已知限制**（第二轮已记录，这轮定位得更准）：
> 沙箱 shim 的 `_safe_rmdir` 每次耗时约 **30 秒**（栈落在 `sitecustomize._safe_rmdir`），
> 所以含大量 `TemporaryDirectory` 的测试文件（`test_workspace` / `test_resume`）跑不完。
> 已用栈证明与代码改动无关；已放后台长时跑。

## 七、给下一次审查的三条

1. **判据要按"形状"写，不要按"某一个已知写法"写。**
   本轮的 `board.py` 漏网就是因为判据写成了查 `run.py` 的那个字面量。
   换成"括号里同时出现三个阶段名"之后，任何写法都跑不掉。
2. **"两处各写一遍"要用测试守，不能靠注释提醒。**
   `gui/jobs.py` 里那句"不许出现这里没有的东西"存在了很久，从没起作用。
3. **静默失效优先于崩溃。**
   本轮修的每一条（阶段参数名、上游血缘、退出码语义）都是"不报错、只是结果不对"。
   崩溃会有人看见；静默不会。审查时**优先找静默的**。
