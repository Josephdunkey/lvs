# 编排框架审查 · 外部对标（第五轮）

> 需求：**参考 GitHub 上优秀的 agent 编排与视频制作 agent，看这套编排框架有没有问题，有问题就改。**
>
> 方法：先联网调研外部参照（不是凭印象），再把它们的做法**逐条对本框架核一遍** ——
> 靠读代码能回答的自己答，只把真正的缺口动手改掉。**不为了"像别人"而改。**

## 一、看了什么（外部参照）

| 来源 | 关键架构 / 结论 | 对本框架的意义 |
|---|---|---|
| **ViMax**（HKUDS，9.8k★） | 四角色（编剧/导演/制片/生成）；**一致性专层**；**中间产物是文件**，可审可改；render checkpoint + 持久化渲染状态 | 我们的定妆库（G2）+ `_v2/` 稿 + 门禁账本，方向一致 |
| **StoryFlow** | **分镜强制 JSON Schema**（"LLM 输出不稳定是流水线最大坑"）；**每镜头独立生成再拼接**；字幕按实际时长动态校准 | 逐镜失败隔离已有；**Schema 强约束我们缺了一半**（见 §三.1） |
| **OpenMontage**（44k★） | **质量门禁贯穿全程**：黑帧检测 / 静音分析 / 字幕存在性 / 时长与承诺一致性；失败就不当作交付物 | 我们只有逐片段校验，**整片终检缺**（见 §三.3） |
| **LangGraph 系 2026 实践** | checkpointer 跨进程恢复；`interrupt()` HITL；**Circuit Breaker**；token/迭代**硬上限** | HITL 门禁已有；**熔断缺**（见 §三.2） |
| **MAST 报告**（1642 条执行轨迹） | 失败分布：**系统设计 41.77% / 交互错位 36.94% / 任务验证 21.30%** | "交互错位"我们缺（见 §三.1）；"验证"缺整片层（§三.3） |
| **多 agent 生产实践（2026）** | canonical handoff schema；ACCEPTED/REJECTED 信号；per-step timeout；cross-agent trace；**别为架构优雅硬上多 agent** | 交接契约缺（§三.1）；信号我们已有（`StageResult` + 门禁） |

**一句话结论**：本框架的**骨架是对的**（持久化产物 + 人审门禁 + 逐件隔离 + 断点续跑 +
单一真源），外部项目最看重的几件事我们都做了。真正的缺口**不在架构形状，在三处"交接与兜底"**。

## 二、逐分支核对（哪些是真的缺）

| 决策分支 | 外部做法 | 本框架现状 | 结论 |
|---|---|---|---|
| 产物是否可审、可改 | 中间产物落文件、人可改 | `shots.json` / `_v2/` 稿 / `parse.json` 全是文件 | ✅ 已有（且更强：门禁指纹绑定） |
| 人在环（HITL） | `interrupt()` / checkpoint 等批 | 六道门 G0–G5，fail-closed，指纹失效 | ✅ 已有 |
| 断点续跑 | 不重放已完成节点 | `manifest` + 产物血缘（含目录） | ✅ 已有（第四轮补齐目录血缘） |
| 逐件失败隔离 | 每镜头独立生成再拼接 | assets/tts 逐镜隔离 | ✅ 已有 |
| **阶段间交接契约** | 强制 schema + 接收方校验 | `shots` 自己生成时校验；**下游消费时不校验** | ❌ **缺** |
| **系统性故障止损** | Circuit Breaker + 硬上限 | **无**（服务挂了会逐镜失败到底） | ❌ **缺** |
| **整片终检** | 黑帧 / 静音 / 字幕存在性 | 只查**逐片段**（`assert_segment_rendered`） | ❌ **缺** |
| 统一的失败信号 | ACCEPTED / REJECTED | `StageResult` + 门禁，**但退出码语义有 bug** | ⚠️ **文档与实现不符** |
| 单一真源 | （工程共识） | `stage` / `errors` / `artifact` / `styles` | ✅ 已有（第三、四轮） |
| 是否该上"多 agent" | **别为优雅硬上**，确定性逻辑用代码 | 本框架是"确定性流水线 + LLM 只在拆镜"，**没有**盲目多 agent 化 | ✅ 判断正确 |

## 三、改了什么（四处，都有真机证据）

### 3.1 阶段间契约（`lvs/handoff.py`，新增）

**问题**：`lvs shots` 生成 `shots.json` 时会跑 `_validate`，但**下游消费时不校验**。
`shots.json` 是**给人手改的真相源**（设计如此），一旦有人手改坏了，`tts` / `assets` / `build`
会各自 `.get("narration")` 兜空按默认值继续 —— 产出的成片**不报错，只是错**。
这正是 MAST 报告里占比 36.94% 的"交互错位"：一个环节的坏数据成了下一个环节的事实前提。

**改法**：把"一份分镜表必须长什么样"抽成**一处**（`VALID_SOURCES` / `REQUIRED_FIELDS` /
`validate_shots`），产出方与消费方共用；下游拿到就验，不合格**点名是哪个上游产的、缺什么、
该重跑哪条命令**，而不是在下游深处抛一个看不懂的 `KeyError`。

- 校验器只报"**一定会让下游出错**"的问题（漏报=白做，误报=失去信任 —— 这条在本项目反复吃过亏）
- 刻意**不误伤**合法形态：`graphic` 镜、`start` 为 `None` 的静音镜、空表都算合法
- `handoff.VALID_SOURCES` 与真源（`sources.MODES` / `prompting.KIND_GRAPHIC`）由**架构测试**对齐

### 3.2 连续失败熔断（`lvs/breaker.py`，新增）

**问题**：逐镜隔离只解决"单件坏"，没解决"**系统性坏**"。ComfyUI 没起来 / 显存被占 /
TTS 掉线时，每一镜都会失败，而流水线会**一镜一镜地失败到底** —— 654 镜就是 654 次超时。

**改法**：`Breaker`（连续失败到阈值即停，中间成功一次即清零）。接进 `assets` 与 `tts` 的逐镜循环。
语义边界写进了代码注释与消息：
- **只跳过失败，不跳过人审门禁**
- 是"这一批先别跑了"，不是"永久禁用"
- 阈值可配，`0` = 关闭

### 3.3 成片终检（`build.final_sanity` + `ffmpeg` 三个探测助手）

**问题**：`assert_segment_rendered` 查的是**每个片段**；整片才有的故障（音轨整体丢了 /
整片静音 / 整片黑屏）**逐片段查不出来** —— 而它们恰恰是"流水线坏了"最强的信号。

**改法**：新增整片终检（做法对标 OpenMontage）：
- **硬检查**：成片无音轨 → 判失败（旁白丢了）
- **警告**：整片平均音量 ≤ -60 dB（静音）；整片黑屏占比 ≥ 80%
  （有声书式全黑配图是合法风格，所以只报不拦）
- **读不到就跳过**：宁可不报，也不要因工具环境问题拦下一部好片

三个探测（`has_audio_stream` / `mean_volume_db` / `black_ratio`）全走 ffmpeg 分析 filter，
**不落临时文件**，已在真实生成的三段媒体上验证（正常 / 全黑静音 / 无音轨）。

### 3.4 退出码语义：文档与实现不符（已修）

**问题**：`errors.py` 定义 `EXIT_FAILED = 1`（"跑完了但有失败件"），
但 `assets` / `tts` **无论有没有失败件都 `return 0`** —— 于是这个退出码形同虚设，
脚本与 `lvs run` 都以为一切正常。**又是"文档当愿望用"**（第三轮在 `--keep-going` 上踩过同一个坑）。

**改法**：
- Three 阶段有失败件就返回 `EXIT_FAILED`（`assets` / `tts` / `build` 有占位镜）
- `StageResult` 加 `partial` 属性；`run.py` 据此分类：
  | 退出码 | 含义 | `lvs run` 的行为 |
  |---|---|---|
  | 0 | 成功 | 继续 |
  | **1** | **有失败件（逐镜）** | **继续**（这是逐镜隔离的本意），最后汇总返回 1 |
  | 2 | 输入/前置条件不对 | 停下（`--keep-going` 可跳过） |
  | 3 | 人等门禁 | 停下（`--keep-going` **也不跳**） |
- `--keep-going` 的说明相应澄清：它管的是**硬失败**，逐镜部分失败本来就继续

## 四、刻意**没有**改的（以及为什么）

| 没改 | 理由 |
|---|---|
| 保持"确定性流水线 + LLM 只在拆镜"，不引入多 agent 框架 | 2026 生产实践的**第一条**建议就是"别为架构优雅硬上多 agent"；确定性逻辑用代码比用 agent 好。本项目正是这么做的 |
| 不引入 LangGraph / CrewAI / AutoGen | 同上 —— 本流水线是**有向无环的阶段序列 + 人审闸门**，用图框架只会增加依赖与学习成本。只要满足"持久化 + HITL + 断点续跑"，自建更贴合 |
| 不加"跨进程 checkpointer" | 我们已经是"文件即状态"（`manifest` + 产物），天然跨进程；引入数据库反而是**多一个失同步的真源** |
| 拆 `run_command` 成 `核心函数 + CLI 适配器` | 上一轮 P0 遗留；本轮确认它是**可维护性**问题、不是"会出错"问题，风险中，不在本轮范围内 |
| 加 token 预算硬上限 | 本流水线 LLM 只用于拆镜（一次性），不是多轮 agent 循环，风险远小于多 agent 系统。可作为 P2 |

## 六、给下一次审查的三条

1. **外部对标要先看"他们的失败分布"**，不是先看他们的功能表。MAST 那份 1642 条轨迹的分布
   （设计 41.77% / 交接 36.94% / 验证 21.30%）比任何 feature list 都更能指出该补哪里。
2. **"我们缺什么"要用代码核实，不能用印象**。本轮三个缺口都是靠"读下游怎么消费上游产物"找到的，
   而不是靠对照别人的 README。
3. **优先修"文档与实现不符"**。`EXIT_FAILED` 定义了却从不被返回 —— 这类问题不报警、不崩溃，
   但会让所有上层判断（脚本、CI、`--keep-going`）**建立在假前提上**。
