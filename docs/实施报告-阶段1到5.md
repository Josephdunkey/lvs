## 逐项：做了什么 / 为什么这么做 / 怎么验的

### ① manifest 原子写 + 写回节流

**改了什么**：`_write_manifest` 从 `write_text`（先截断再写）改成
**临时文件 → `fsync` → `os.replace`**；`mark_stage_progress` 加写盘节流。

**为什么**：截断窗口 + `_read_manifest` 遇到坏 JSON 会**静默重建成空** ——
两者叠加的后果是"写盘途中被打断 → **断点续跑记录全丢**"。而
`mark_stage_progress` **每镜调一次**（654 镜 = 654 次整文件重写）放大了这个窗口。

**踩过的坑（自己抓到的）**：第一版节流用"**完成数变了**"当条件 ——
而 `done` 每镜都 +1，于是 300 次调用写了 300 次，**节流形同虚设**。
改成"**百分比跳格 或 超时间窗口**"后降到 101 次。

**验证**：`test_manifest_atomic.py`（9 例）；300 次进度调用 → 101 次写盘；
`os.replace` 失败时**不崩**（吞掉并清理临时文件）。

### ⑤ 离线端到端

**改了什么**：
- `tts.SilentTTSBackend`：按字数估时长（4.5 字/秒 + 标点停顿），ffmpeg 生成静音轨
- `assets._placeholder_png` + `[comfyui].backend="placeholder"`：ffmpeg 造占位图
- `tests/test_e2e_offline.py`：16 例，整链跑通

**为什么**：真机跑一次是**数小时**，不可能每次改动都跑。但"整条链还接得上吗"
恰恰是跨阶段的、单元测试测不到的（本项目历史故障多是跨阶段的）。

**关键设计**：离线**只换"像素/声音从哪来"**，阶段编排、逐镜循环、失败隔离、
契约校验、产物血缘、成片终检**全是真实代码** —— 自己造假产物就等于没测。

**顺带发现并修的**：`voice` 走 GPU 守卫时没排除 `silent`（它不用显存）；
`voice` 的 `mark_stage` 没传 `total`（被 `--json` 的信封暴露成 `done=3 total=0` 的矛盾数）。

**验证**：真机 `lvs run --demo` 退出码 0、成片 11.2s、重跑幂等（合成 0 / 跳过 3）。

### ③ 结果契约

**改了什么**：新增 `lvs/result.py`（统一信封）+ 给 7 个命令加 `--json`
（parse / shots / assets / voice / build / run / qc）。

**为什么**：此前"成了吗 / 坏了几件 / 下一步敲什么"只在**中文散文**里
（「素材获取完成：新取 651，跳过 0，失败 3」）—— 程序要读就得正则中文，
**措辞一改脚本就断**。

**契约边界（用户拍板）**：只锁 **5 个决策字段**
（`ok` / `status` / `exit_code` / `counts.failed` / `next_hint`），其余自由扩展。
`exit_code` **复用 CLI 同一个值**，不另立一套。

**验证**：`test_result.py`（19 例，含"exit_code 必须等于真实退出码"）+
架构判据 `test_every_work_command_supports_json`（防止将来新增命令漏加 `--json`）。

### ④ 门禁自动判据

**改了什么**：新增 `lvs/criteria.py`；`GateStatus` 加 `criterion_ok` / `criterion_reason`；
`open = 人已批准/跳过` **AND** `自动判据通过`。

**为什么（这是本轮最实的一个发现）**：G3 的说明写着「全部图 **+ 巡检结论**」、
`why` 写着「每块 24 张过眼」，而 `pipeline.subjects()` 对 G3 **只返回 `assets` 目录**、
`pipeline.py` 里 `qc` 出现 **0 次** ——
**可以跳过 `lvs qc` 直接批准 G3。门禁比它承诺的更松。**

**语义（刻意不搞反）**：这是**必要条件**，**严格加强**：
判据通过仍需人批准；人批准但判据没过 → **仍不放行**，并说明缺什么、跑哪条命令。
G0 / G2 / G5 **刻意不设**判据 —— 它们本质上是人的判断，硬塞机器判据只会变噪音。

**验证**：`test_criteria.py`（17 例），核心断言
`test_approved_but_criterion_failed_still_not_open`；
真机验证：批准 G3（未跑 qc）→ 状态显示"已批准"但**明确标注仍未放行**，跑完 `lvs qc` 后自动放行。

### ② 可观测性最小版

**改了什么**：`lvs/runlog.py`（`logs/run-<日期>.jsonl`，一镜一行）+
`Workspace.record_timing`（耗时落 manifest 的 `last_seconds` / `total_seconds`）。

**为什么**：跑 8 小时崩了之后，不该只剩一屏滚掉的 stdout。
"哪一镜开始出问题、是不是同一类错误连着来、熔断停在第几镜" —— 一个 654 行的
JSONL（~100 KB）就能回答。**不上框架、不起服务**。

**关键设计**：`stage.note_stage_end` 是**两条入口共用的单一实现** ——
`run`（走 `run_stage`）与**直接敲单条命令**（`cli._run_and_report`）。
分开写会导致"逐条驱动"和"一键 run"的轨迹不一样，而 **agent 恰恰是逐条驱动的**。
（第一版就是分开写的，审查时发现单命令路径没记 `stage_end`。）

**验证**：`test_runlog.py`（16 例，含"两条入口共用同一实现"的源码级判据）。

## 代码审查：用**另一套判据**审自己的改动

按项目纪律（"审自己的改动要换一套判据"），本轮专门扫了**"定义了却从不接线"**
—— 这是本项目最大的坑型（第四轮 `EXIT_FAILED` 从不被返回、第六轮 `exit_code_for`
从不被调用）。结果：

| 发现 | 性质 | 处理 |
|---|---|---|
| ★ `flush_manifest()` 生产代码 **0 处调用**，而文档写着「**收尾时必须调它**」 | **文档说谎 + 死代码** | **删除**，并把 `mark_stage_progress` 的文档改成事实（收尾那条 `mark_stage` 不节流，最终状态一定落全） |
| `criteria.has_criterion` 只被测试用 | 半接线 | 接进 `statuses_json`（agent 据此知道"光批准还不够"） |
| `runlog.failures()` 只被测试用 | 半接线 | 接进 `run.py` 的失败汇总 —— 长跑挂了直接打印最近几条逐镜失败 |

`runlog.read` 仍只在测试与模块内（被 `failures()` 调用），符合"给上层决策用的函数
要么有调用点、要么在测试里"。

## 一个需要说清的边界

`--json` 时**人类可读的散文照旧会先打出来**，信封是**最后一段**。
即 agent 应当只取最后那段 JSON（以 `{` 开头）。
这样"给人看"与"给机器读"都不牺牲，也不必给每段散文加开关。
若将来觉得混在一起不便，再加 `--quiet` 单独输出 JSON（未做，避免过度设计）。
